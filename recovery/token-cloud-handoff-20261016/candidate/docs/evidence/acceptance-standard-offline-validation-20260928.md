## 输入与机制

新逐切片任务在第一张卡前，从正式 `product.md` 提取 `docs/acceptance-standard.json`。每个条目有程序分配的 ID、产品原文连续引用、动作／条件和可观察结果；程序拒绝不存在于原文的引用，再由独立模型请求对照完整产品需求检查遗漏、合并和曲解，最多两轮内部纠正。生成结果绑定正式产品哈希，旧逐切片任务不自动迁移。

Slice Planner 接收内部标准，卡片必须声明实际覆盖的条目 ID。Developer 接收当前卡关联的原文与结果。`complete` 先确定性检查每个条目是否有已通过切片归属，再由独立审查核对切片验收、真实测试反馈和生成的浏览器脚本。审查报告保存行为 ID 到切片、测试报告和脚本哈希的映射；审查发现缺口时给 Planner 具体反馈继续规划。首次产品验证和返修后脚本／代码变化时，旧覆盖审查不能作为当前版本的通过依据。

## 限制

本轮没有真实 Provider 的提取或独立审查响应，不能宣称模型一定能完整提取产品行为或准确判断脚本覆盖；Fake 验证只证明状态和门禁按协议工作。旧内容工作台产物仍缺页面编辑功能，旧失败任务未续跑。新机制对未来新任务的真实效果、额外 Token 成本与用户验收均未验证。自由文本的语义完整性不能仅靠原文引用和编号确定性保证，最终仍需真实浏览器操作及用户验收。
