# 必要读取进展与当前任务焦点

## 用户决定与历史核对

用户同意前次建议的第２项「必要读取不算停滞」和第３项「当前任务上下文整理」，并补充第１项通过后催促提交是为了解决过去反复查看同一代码的问题。本轮保留已有催促提交和实际版本保护，不实施取消方案，不自动替模型结束或提交。

历史确有记录：`current-only-context-validation.md` 的 2026-09-17 去重固定设计实验，100 次 HTTP、571,166 Token，加法／平方程序单元测试通过，UI 文件生成后持续读取至调用上限；产物经独立 Node 18 项和 Chromium 18 组验证通过。但 UI 自动交接与最终自动验证当时未完成，不能概括为「所有自动自测都已通过」。架构问题 004 保存了该触发原因以及后续显式提交方案。

## 实现范围

- 先更新 Dev Design，再修改现有 Worker。成功读取按规范路径、文件 SHA-256 与实际返回行数判定新信息；同版本已提供区间合并后完全覆盖新请求，则不发放读取进展。失败／被阻止读取、路径别名、仅改描述不算新信息。截断结果只按实际返回部分判断，空结果不提供新行范围。
- 将读取进展持久化为检查点字段 `unit_read_information_progress`，按模型批次更新连续停滞。一个批次中的真实文件变化或新信息使该批次不算停滞；同字节写入仍不重置。请求字段改为符合其语义的 `unit_no_progress.calls_without_progress`，保留四批提醒、八批停止、内容去重、相同动作、总模型预算与原有提交规则。
- 请求最前增加 `current_task`：原始目标引用、原卡业务依据与当前执行职责的视图、最近证据来源及版本适用状态、缺文件／待自测／待提交／待独立目标核验。完整卡片、目标与错误只在已有字段保留，不复制全文。
- 原卡和批准业务验收不做自然语言替换。有效执行视图明确覆盖旧卡中的服务托管与日志要求，模型仍负责在原权限内纠正冲突测试。此实现不是语义重写原卡，也没有预先证明旧测试已修正。
- 激活不可变 `slice-developer/v10.md`：先读当前任务焦点，围绕真实失败读取必要范围，同一根因修改后尽早自测；过期报告不能当成当前版本失败，开发阶段不能自行关闭原目标账本。保留 v9 及现行通过后提交要求。

没有新增模型调用、摘要模型、数据库或 Provider 变更，没有续跑旧任务。信息进展只说明取得此前没有的范围；程序不能证明每个新范围在业务上必需，也不能仅凭新信息证明代码完成。模型仍可耗尽总预算，稳定收敛未验证。
