## 建议：程序生成一份当前任务事实

推荐在新repair-v1模型请求中建立单一事实视图，由原runtime、完整检查点、当前manifest和原目标账本确定性投影；不增加模型总结调用，不增加数据库schema，不新建第二套事实存储。原始协议、思考、Trace、工具账本继续留存。

| 内容 | 程序提供的事实 | 不得代替模型作出的判断 |
| --- | --- | --- |
| 任务 | 原反馈一份、授权范围、当前阶段、未回答决定 | 不另写需求或擅自扩大范围 |
| 当前修改 | 本次尝试累计成功修改，按文件记录仍对应当前版本的修改引用 | 修改成功不等于业务正确，不用模型描述自动核销目标 |
| 自测 | 唯一状态：未测／失败／当前通过／已过期；命令、计数、版本依据、明确类型的原日志引用 | 不因测试通过认定功能全覆盖 |
| 提交条件 | 程序门禁的真实阻塞、仍需模型显式提交 | 门禁无阻塞不等于业务已完成；模型仍可修改 |
| 待执行验证 | 提交后由程序执行的独立测试、浏览器、目标审查，明确尚未运行 | 不能预报通过，也不能提前关闭原始目标 |
| 当前文件正文 | 当前实际可见版本和行范围，未携带／截断如实标注 | 不把未读内容当作已读全文，不禁止必要补读 |

关键区别：当前任务进度包含仍适用的累计修改，不再等同最后一次接力的区间摘要。诊断证据只用一个明确的当前结果入口；model_call_id、tool_call_id、summary_id保留明确类型，不要求模型比较不同ID来推断先后。原目标保持open，但说明「待提交后的独立核验，当前业务完成程度由模型判断」。

历史工具摘要不作为与当前状态平级的默认事实输入，完整原审计仍可按权限查询；当前实际文件范围和重复读取判定必须保持，不能因收窄历史摘要错误拒绝有效读或重新授权原本禁止的文件。

## 为什么不选另一条路线

另一候选是完全取消接力、始终重传所有历史，使模型自然保留叙事。此方案能减少重建进度的需求，但长任务输入会持续增长，且不能忽略DeepSeek当前对话思考／工具配对要求。暂不推荐将它作为默认策略；不能未经对照断言哪种一定更有效。

推荐先改事实表达，而非引入新角色、再加一个总结模型、自动提交或设「成功后禁止工具」。改动范围限新返修请求投影，旧任务、工具权限、原协议结果和外部API／前端不随之改变。这是涉及模型上下文契约的设计建议，需用户确认后才能实施。

１．先更新有效Dev Design，明确各事实来源、优先级、状态及失效规则。保留用户对产品／工程关键决定的职责。
