# 真实返修提交延迟：逐轮分析与最小修正

日期：2026-10-09。用户批准分析此前真实失败／成本，并在明确原因后做最小修正。本轮不追加真实模型实验。

## 结论与证据边界

找到可复现的机制问题：修改和自测分属不同模型请求，接力只收集自测所在批次的修改，所以两次真实新上下文的 `recent_changes` 都为空。模型实际思考反复怀疑「是否前一个会话修过」「测试是否先于测试文件修改」，在已经有当前版本真实通过证据后继续确认。代码逻辑及两份实际请求可核对这个缺口；它与提交延迟一致，但不能在没有新真实对照时断言修复能省下全部后续请求。

不是所有后续工作无效：英语关键词在笔记中大小写匹配的专项回归有合理价值，新增后必须重新自测；页面装配／存储是首次读取，也可能是必要风险核对。文件尾部并没有被接力携带，补读不属于已经在上下文的重复读取。本次不为省 Token 将这些范围伪称全文或禁止补测。

原实测执行15轮、379,960 Token；随后独立审查1轮、50,945 Token，总430,905 Token。第6轮实现修复后自测149项通过，之后第7—15轮累计258,166 Token，但不能把这部分全部认定浪费；新增专项测试后第11轮150项通过，之后第12—15轮仍用112,636 Token才提交。

## 信息缺口及提示问题

1．`DeepSeekContextRelay.complete_batch`原来只扫描boundary_request_id所在批次。实际第5轮replace、第6轮自测；第10轮replace、第11轮自测，导致第7、12轮recent_changes为空、diagnostic_ref为null。代码正文与当前通过状态存在，但缺少简洁的修改→自测因果记录。

2．通用提示「不得把历史执行成功当作当前代码已验证」没有区分旧成功和程序已核对同版本的真实自测。实际新会话明确读到current_version_passed=true，同时仍反复担忧测试是否在修改前。不能据此证明是唯一原因，但这个提醒的作用范围需要澄清。

3．计划更新工具契约本身完整且模型之前正确使用steps，不是系统没提供schema；第13轮是模型实际参数错误。更新计划不是提交门禁，却占用独立调用和纠错轮次。可提示必要计划更新与提交同批，无需另设自动完成计划状态。

## 已确认并实施的最小修正

先更新有效Dev Design，再修改实现：

- 接力扫描上一可核对完整边界之后直到当前完整批次的成功write／replace，携带修改路径、模型调用ID及工具调用ID。旧边界不完整时拒绝猜测／新建边界，保留原完整协议。
- 接力附当时自测命令、通过状态及测试前后版本是否一致，明确仍是同一逻辑任务。当前适用性仍以worker完整产品版本判定为准，旧通过不会覆盖后续变化，未声明业务目标自动完成。
- 新返修提示区分旧成功与当前已核对通过证据，接力本身不会令有效证据失效；旧流程保留原历史成功提醒。
- 明确计划更新不是提交前置条件；必要时按steps／reason与submit同批，submit仍必须最后。没有强制提交、删除思考、自动推断业务完成或禁止必要阅读／修改。

涉及 `context_relay.py`、`repair_session.py`、`worker.py`。不改共享产品、数据库、授权预算或独立验证职责。
