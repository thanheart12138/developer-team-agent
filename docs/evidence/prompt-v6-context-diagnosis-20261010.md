## 排除与保留

- 不支持根因丢失、历史思考删除、错误HTTP计数、工具read片段hash混用导致第4—7次延迟等归因。
- 支持已有修法后行动仍延迟、HTTP余量正确但未适配收尾的事实。
- 较大的逻辑预算与实际HTTP同时出现可能干扰决策；历史中的结论未被结构化标记可能降低显著性。两者只是候选原因，没有反证实验，不宣称根因确定。
- 8次固定预算揭示效率问题，但不足以证明放宽后无法完成。用户第一目标是完成，不能以拒绝读取、自动提交或伪造完成来换Token降低。

## 下一步最小建议（待用户确认，未实施）

只调整主返修会话的预算视图：呈现本任务实际有效剩余HTTP，并同时列出程序能证明的收尾事实（当前自测是否有效、是否仍需显式提交）。原逻辑预算继续内部限制与审计，模型执行视图避免另一个更大的可用额度入口；其他非返修流程不改。

预算临近耗尽时提示已有自测／提交步骤尚缺以及调查会消耗余量，不强制写文件、不禁止必要读取、不主动测试后提交、不自动追加预算。提示只陈述程序可证实事实，业务完成仍由模型判断，模型未记录的根因不由程序猜测提取。

这比继续叠加「优先修复」文字更直接连接实际执行余量与交接责任，但不保证有效。确认后先修有效设计，再局部实现、离线验证预算／旧会话边界，然后另行批准真实同起点对照。012仍未完成。
