# 自媒体选题与发布计划平台：逐请求成本与流程分析

日期：2026-10-10。性质：完成现场的离线统计及分析，本次新增真实模型调用为零。本报告未实施优化。

## 结论

本轮成本明显偏高。183 次实际 HTTP 的已知用量为 **16,349,587 Token**，另有第 16 次请求用量未知，不能按零成本解释。主要负担来自长上下文在多次执行中反复作为输入发送；新生成的代码、文字和思考仅占总量的小部分。

已知输入 **15,560,808 Token，占 95.18％**；输出 **788,779 Token，占 4.82％**。输入缓存命中 **2,210,304 Token，命中率 14.20％**，未命中输入 **13,350,504 Token**。不能用 Token 总量直接推算付款金额，缓存输入、普通输入、输出的计价可能不同，本报告未读取账单或核算实际费用。

第一卡 6,123,641 Token，第五卡及其返修 5,575,569 Token，合计占总量 **71.56％**。优化应先针对这两条长执行链及其上下文构造，不能仅把问题归为“DeepSeek 不会写代码”或简单禁止重复读取。

## 证据与统计口径

原始现场：`workspace/experiments/editorial-platform-fullflow-20261010/`。

- `http-ledger.json`：发送前持久记账，183 条；`call-count.json` 为 183，总授权 200，失败和重试也计入。
- `sent-requests/001.json` 至 `183.json`：实际发送正文，用消息、模型、工具、thinking 的规范化哈希匹配 SQLite 中的请求 Trace。

- 请求正文匹配无歧义键；未知响应保留。182 次有 usage，第 16 次中断未取得 usage。供应商账本保留缓存及思考字段，不能用 Trace 中已脱敏的嵌套字段代替。
- `request-statistics.csv`：全部 183 次请求的序号、阶段、提示词、会话、状态、耗时、输入／输出／思考／缓存、执行阶段。

统计的是供应商报告的处理量，历史内容每次作为输入都会再次计数。字节与 Token 分开统计，不将字节直接换算成 Token。工具结果成功也不等于测试通过或业务验收成功。

思考占输出约 72.12％，占总量仅 3.48％。因此只关 thinking 不足以解释或解决 1,600 万总量；其对完成率的影响也未做本轮对照。

实际发送消息的 UTF-8 JSON 累计体积：system 1,274,653 字节，user 11,772,114 字节，assistant 24,088,394 字节，tool 19,869,597 字节。assistant 中 `reasoning_content` 累计 14,892,379 字节；这属于历史重传体积，不是新增思考 Token，不能与供应商输出计数直接相加。

仅工具 `content`：累计 18,811,060 字节，其中此前请求已出现过的相同正文累计 17,509,072 字节，占 93.08％；同一个请求内相同工具正文重复累计为零。主要表现为**跨请求重传历史**，不是单次消息列表重复塞入相同工具内容。

182 对连续请求中，153 对只保持第一个完整消息相同，29 对连第一个完整消息也不同；没有一对连续请求的前两个完整消息都相同。请求 27→28 的第二条 user 消息变动包含 `tool_summaries`、`model_call_id`、`recent_model_call_id`、调用预算及文件清单。同期输入 63,327／64,503 Token，缓存命中均仅 6,656 Token。

**机制推断，尚未做对照验证**：频繁变化的 user 上下文位于保留历史之前，可能使后续长历史难以复用长缓存前缀。完整消息不同不等于内部字节前缀完全不同，本统计也未提供供应商缓存分块证据，因此不能宣称已精确计算每个动态字段造成的缓存损失。

不能随意删掉未闭合工具调用链要求的思考或工具结果。应区分完整审计留存与下一次推理输入；能否在安全边界重新组织上下文，需要先验证供应商协议及业务信息完整性。

## 六、重复读取与工具行动

模型检查点去重后共 218 次工具行动：read 98、write 25、replace 76、run_unit_tests 11、submit_unit_for_test 7、get_file_change_history 1。程序执行的 exec 另有 27 条，不能误算成模型主动调查 27 次。

产品读取中具有版本哈希的为 97 次，其中 **22 次同路径、同文件版本、同起止范围重复读取，占 22.68％**。该口径不包括不同区间的重叠读取，也不把修改后的重读当重复。重复读取确认存在，但其返回体积及连带历史成本不能仅按 22／97 推算。

读取热点：`verify_product.py` 23，`domain/plans.js` 8，`domain/topics.js`、`domain/tasks.js`、对应 tasks／plans 测试各 5。精确重复可能用于编辑定位或工具恢复，需按当时待办判断是否必要；不能只凭次数批量禁读。

## 七、明确故障与可避免开销

1. **实验沙箱适配错误**：阶段文件的语法检查／测试路径未正确接入，已有有效骨架被程序拒绝，导致反复生成。请求 13—15 的已知处理量共 188,493 Token，第 16 次未知。这个量表示受错误影响的请求处理量，不能全部等同净可节省量，因为正常流程仍需生成及验证骨架。责任属于实验适配，不能归因模型。
2. **输出截断**：请求 25 输入 27,086、输出 65,536、总计 92,622 Token，其中思考 64,839；工具 JSON 截断，Trace 为 `invalid_tool_call`，未形成有效修改。下一请求 26 才首次有效写入。大输出上限并没有避免这次无效往返。
3. **限额与恢复**：119 次 HTTP 时触发开发阶段 100 次逻辑调用上限。用户授权隔离进程扩展为 200 并继承原计数／检查点，随后到 183；正式 Worker 没改。总 HTTP 仍 200，没有重置账本。这是执行控制与实验配置的问题，不是 HTTP 额度自动消失。
4. **交接状态**：一次提交因自测版本过期失败；随后重新按当前文件通过及提交。不能将“工具返回成功”“之前测过”当成当前版本可交付。

## 九、建议优先级及验证方式

以下均为开发助手建议，**未在本次授权中实施**。

| 优先级 | 建议 | 必须守住的条件 | 验证方式 |
| --- | --- | --- | --- |
| P0 | 真实调用前离线预检所有阶段路径、语法检查、Node／浏览器沙箱入口 | 不以绕过门禁代替修正适配 | 固定骨架全路径预检，不消耗模型 HTTP |
| P1 | 审计请求组装：把可长期稳定的协议／历史和高频变化的状态明确分开，删除不参与语义的临时身份字段须先确认 | 不破坏工具调用协议、最新状态、产品目标或文件版本 | 同一合法断点实际发送体对比；再在授权预算内做缓存命中与完成率对照 |
| P1 | 第一卡按真实依赖闭包重新评审，第五卡按删除／空状态的具体用户路径定位膨胀来源 | 不人为增加角色和卡片；不遗漏关联规则 | 对照原行为标准，检查接口可否独立实现，以及第五卡每次修改对应哪个真实失败 |
| P1 | 对测试脚本维护建立失败定位依据，优先局部修复 | 验收预期来自已批准需求，不通过删除断言“省钱” | 每次修改绑定失败场景、当前版本和修复结果；独立用户操作验收 |
| P2 | 对同版本同范围重复读取提供已有内容位置和版本提示 | 不硬禁必要重读；允许新版本或新证据读取 | 统计有效修改前重复读减少量及新增缺陷，不能只统计请求更短 |
| P2 | 当前版本通过后提供明确剩余目标，提交只携带必要版本／目标证据 | 模型仍有真实修改需求时允许修改并重测 | 减少过期提交失败；按原阶段边界统计通过到提交成本 |

第一目标仍是完成任务，第二目标是降低 Token。下一轮不能只用“平均请求更短”作为成功条件，应同时报告需求覆盖、独立验收、无人工返修比例、总 HTTP、已知与未知用量、缓存命中、三个执行阶段成本。任何节省百分比都需同范围对照，不能用本轮汇总直接保证。

## 统计自检与局限

183 条 CSV 与账本计数一致；输入＋输出＝16,349,587；缓存命中＋未命中＝15,560,808；阶段表与执行阶段表各自相加均为总量。未知请求独立列出。原始 ledger、发送正文、Trace、检查点和数据库未由本次统计改写。

没有实际付款金额；没有随机重复实验；没有测出关闭 thinking 或上下文重排后的成功率；没有将所有重复历史判为冗余；本次未完成独立业务验收。结论是本轮已观察到明显的上下文及执行链成本问题，尚不能证明任一优化能在其他任务上稳定提高完成率。
