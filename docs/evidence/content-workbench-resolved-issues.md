# 素材管理流程已解决问题与解决过程

日期：2026-09-20。范围：记录本轮素材管理全链路及局部验证中已经有代码修复和验证证据的问题。“普通开发阶段 DeepSeek 持续读取”在后续控制流切换中取得一个真实局部成功样本，见第七项；稳定性和完整产品交付仍未验证，不把局部结果外推为全链路成功。

## 1．文件工具参数别名导致首次写入失败

### 问题发现

从空工作区运行素材管理全流程时，Developer 已生成 storage 实现与测试，但调用文件工具时使用 `file_path`。查询工具使用该字段，而 `read`／`write`／`replace` 当时只接受 `path`，两次写入均返回参数错误，任务在 20 次 HTTP、147,556 Token 后停止。

### 原因

模型混用了两组工具的路径字段。写入内容和路径意图已经明确，失败来自工具协议中同义参数不兼容，不是业务设计或文件所有权冲突。

### 解决过程

在 `ToolRuntime.execute` 的统一分派入口增加参数归一：`read`、`write`、`replace` 缺少 `path` 且存在 `file_path` 时，将其转换为 `path`。如果两个字段同时存在，仍以正式 `path` 为准。归一后继续经过原有工作区路径校验、单元文件所有权校验和覆盖标志校验，没有放宽写入范围。

### 验证与边界

回归覆盖三种文件工具的别名、正式字段优先级和原安全边界。后续真实主任务越过该故障并完成前两张切片，证明真实模型误用别名不再阻塞写入。该修复不处理非法路径或所有权越界。

## 2．骨架纠正反馈缺少结构信息

### 问题发现

主任务第一次架构骨架生成连续 13 次调用后失败。模型把 27 个文件压缩到 21 个，但通用错误只说明契约无效，没有指出哪些模块含多个实现文件；后续修正又丢失模块接口及 `product/` 路径前缀。

### 原因

Runtime 已经知道具体校验差异，却只返回统一错误码。每次重试都让模型从完整架构重新推导文件结构，既丢失上一候选的有效部分，也无法围绕明确字段修复。

### 解决过程

骨架校验改为返回模块及缺失字段：

- 标识需要合并的多实现文件候选；
- 标识缺失接口和路径前缀；
- 把上一候选的模块／路径轮廓带入纠正上下文；
- 只传结构，不重复文件正文。

### 验证与边界

恢复同一真实任务后，架构骨架通过校验并进入 Dev Design／Develop。该结果证明结构化纠正解决了这次骨架协议失败；它不证明任意复杂架构都能在一次生成中通过。

## 3．已交付模块通过 owners 绕过重复所有权门禁

### 问题发现

第三张 `materials-library` 卡最初把已经通过的基础模块继续列入 `owners`，但 `implementation_files` 只包含 materials 文件。原校验只检查重复文件，因此错误卡片绕过门禁，使切片职责和可写文件不一致。

### 原因

Planner 把“依赖并调用已交付接口”表达成“再次拥有依赖模块”。Runtime 只用文件集合判断重复交付，遗漏了模块所有权本身。

### 解决过程

- `slice-planner/v5` 明确：已通过模块默认只进入 `required_interfaces`，不得重新进入 owners、实现文件或测试文件。
- 真正需要改变既有行为时，必须同时声明 `rework_delivered_modules` 和逐模块 `rework_reasons`。
- Runtime 同时校验 `owners ∩ delivered_modules`，不再只检查重复文件。
- Worker 恢复旧待开发卡时重新执行当前校验；旧卡不合法则自动重规划，不沿用历史错误卡。

### 验证与边界

机制测试覆盖未声明重复 owner 被拒绝、显式返工通过及恢复时自动重规划。真实任务恢复后，第三张卡收敛为只拥有 materials。该修复解决所有权重复，不保证 Developer 会完成卡片实现。

## 4．Developer 不知道已交付接口位于哪个文件

### 问题发现

materials 卡依赖 Search／Validate。Developer 按接口名尝试读取不存在的 `search.js` 和 `validate.js`，而真实实现合并在已通过切片的 `task-view.js` 中。

### 原因

传给 Developer 的 `passed_slices` 只有切片 ID 和 acceptance，没有接口列表与实现文件映射。模型知道依赖已通过，却无法从上下文确定接口的真实文件位置，只能按名称猜路径。

### 解决过程

Developer 上下文中的每个已通过切片补充：

- `interfaces`；
- `implementation_files`；
- 保留原切片 ID 和 acceptance。

依赖文件仍然只读，当前卡可写范围没有扩大。

### 验证与边界

恢复后的真实模型明确识别 Search／Validate 位于 `task-view.js` 并成功读取该文件，原先的路径猜测问题得到解决。之后出现的重复读取属于独立的控制流问题，不能反推映射修复无效。

## 5．测试实现错误时模型不敢修改，修改后又不复测

### 问题发现

`topics-management` 自测仅有一项失败：测试给 tasks 注入回调后，却修改 topics 自己的回调并期待 tasks 行为改变。DeepSeek 已正确定位到测试夹具错误，但提示词强调不得降低或绕过测试，模型继续读取失败片段，没有执行替换。

首次 v6／v7 局部工具对比中，两版都正确修改测试，独立 Node 通过，但修改后继续读取直至预算耗尽，没有主动复测。

### 原因

问题由两部分组成：提示词没有区分“修正错误测试实现”和“削弱测试”；Runtime 也没有在修改后强制把流程转入真实自测。

### 解决过程

- `slice-developer/v7` 明确允许修正错误回调对象、夹具装配、数量计算和环境假设，但必须保持 acceptance 语义和覆盖强度。
- 自测失败后，未修改文件的已读重叠区间禁止重复读取。
- 失败修复发生实际写入后，下一批只允许 `run_unit_tests`；同批仍允许完成同一根因的相关修改。
- 外部恢复的 `unit_test_feedback.passed=false` 与当前历史中的失败自测使用同一状态机。

### 验证与边界

修复后使用相同三文件夹具复测：v6 用 5 次调用、21,511 Token，v7 用 4 次调用、17,495 Token；两版均正确修改、主动复测、Node 1 项通过且模型循环成功。该问题在最小真实工具闭环中已解决。完整素材管理仍受其他 Developer 控制流问题阻塞。

## 6．修改后的失败证据会继续驱动旧版本返修

### 问题发现

素材管理早期全流程中，验证脚本已变化，返修仍携带旧浏览器失败报告反复要求修改产品。调用 154—160 共消耗 426,092 Token。

### 原因

失败报告没有和当时的产品文件版本绑定。Runtime 无法判断报告描述的代码是否还是当前代码，旧错误因而可以跨修改继续生效。

### 解决过程

- 浏览器验证保存报告哈希、结果以及当时全部行为相关文件哈希。
- 进入返修前比较当前文件哈希；一致才把失败交给模型。
- 文件版本不同则由程序直接复跑原验证：通过时零模型返回主流程，失败时用当前输出替换旧证据。
- 普通返修首次写入后立即结束模型循环，由程序复跑原失败验证。

### 验证与边界

机制回归覆盖证据版本保存、过期证据零模型复验和当前失败重新绑定。该修复确定性阻断旧报告继续驱动返修；新的真实全链路尚未进入集成返修，因此实际全链路 Token 降幅未验证。

## 汇总结论

以上六项问题均满足“有失败复现、有原因证据、有代码修复、有机制或真实模型验证”。截至最初整理时，普通开发在读取依赖后仍持续请求 read；五个局部 DeepSeek 样本共 42 次、396,835 Token，均未完成 materials 切片。这些历史失败保留，后续新增验证如下。

## 7．推进错误反馈无法终止旧对话中的重复读取

用户确认改为控制流切换后，Runtime 在首次违反推进约束时结束旧对话，以已校验接口映射、依赖当前版本和 owned_files 启动独立受限实现。模型只修改拥有文件或请求重规划，Runtime 在完整写入批次后直接自测、通过后调用原提交校验，再走独立回归。切换状态和最多四次实现／修复额度持久化，恢复不再开启旧循环。

新增 17 项回归，完整 241 项通过。唯一真实 materials 样本用 7 次有效响应、76,859 Token 完成局部闭环；其中切换后的两次调用分别写实现及真实测试。Runtime 自测和独立 Node 均 26 项通过、零 todo，未修改依赖。额外五组独立验收及浏览器模块持久化通过。

该读取空转在当前真实样本中已被控制流切换解决，不代表模型在普通对话中自行改善。实际页面保存仍因未实现 UI 的依赖引用失败，完整产品未交付；单样本不证明稳定成功率或 Token 降幅。详见 [独立实现验证](materials-control-switch-validation.md) 。
