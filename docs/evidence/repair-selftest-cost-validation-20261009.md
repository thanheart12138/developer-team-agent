## 原因与已确认边界

上一轮素材笔记检索真实返修完成，但 15 请求消耗 629,781 Token。完整 Node 自测结果约 5 万字符反复进入工具协议，修复后没有新修改仍再次执行自测，随后多次检查浏览器脚本才提交。修正规范先写入 `docs/DEV_DESIGN.md`，不改独立测试、原始目标审查、用户验收及模型明确提交要求。

## 实现

- `repair_session.self_test_view`：完整结果仍在 Trace／检查点，模型工具结果从首次发送起使用确定性摘要，包含真实 passed、命令、文件版本、测试计数、退出码／超时／工具错误及原模型调用／工具调用引用。成功不发送全量 TAP；失败保留失败用例诊断，最多 16,000 字符 stdout 与 6,000 字符 stderr，截断明确标注，原日志可分页查询。支持容器 TAP 和本机 Node 的 ℹ 计数格式。
- `project_test_history`：仅投影新返修自测及提交内嵌的自测结果，不改调用 ID、参数、reasoning_content 或原审计。普通读取与按需日志详情不被二次摘要，模型仍可取得完整证据。
- `RepairTools._run_unit_tests`：全产品当前文件集合／内容与原真实通过结果匹配时复用证据，明确 reused=true、未再次执行；实现、测试、集合、命令变化或失败不复用。跨阶段失败恢复沿用原 validation_boundary；独立流水线始终重新测试冻结版本。
- `worker`：主会话 unit_self_test、当前请求数据与实际协议历史使用同一摘要，避免用户上下文再重复工具结果；当前版本通过时提示「原缺陷修复且无未完成修改则提交」，明确浏览器及目标审查由程序负责。必要阅读／修改仍允许，不自动交接。
- 更新执行提示词，因此会话 prompt_hash 变化；原绑定守卫保持，不偷偷迁移运行中的旧会话。之前已完成实测的待验收状态及审计不改。
