## 必要的独立核验

仅运行一次当前生成软件 Node 测试和一次既有行内编辑验收脚本，没有重跑项目后端回归或追加付费请求。

独立 Chrome 在当前预览 `http://127.0.0.1:50048` 验证：素材笔记编辑保存、按新笔记检索、不增加记录、刷新保留；选题角度与高优先级编辑保存、不增加记录、刷新保留；页面异常 0。输出 `MATERIAL_AND_TOPIC_EDIT_ACCEPTANCE_PASSED`。

Node 三项失败已核对：

1．名为 HTML 入口检查的测试还断言脚本含 `ThreadingHTTPServer`，实际失败点是自建服务实现文字要求，不是 HTML 缺失。
2．旧 `--serve` 测试要求验证脚本托管静态服务，与已确认的 Worker 负责启动、验证脚本只使用传入 URL 规则冲突；新脚本拒绝托管，测试等待启动超时。该调用回退到旧硬编码 URL，其浏览器输出不作为本次产品验证证据。
3．传入当前产品测试服务 URL 的真实浏览器路径已实际通过素材／选题编辑、关联、创建任务、工作台、删除确认、刷新等操作；测试失败在要求输出含「使用传入的产品 URL」，新脚本输出「使用产品 URL」。不能把文字匹配失败写成业务操作失败，整体 Node 仍报告失败。

## 结论与边界

### 后续只读排查：交接为何停滞

用户要求继续后，核对开发请求与原始思考：第 2、15、20 次请求均明确给出 `next_action=run_unit_tests`，工具列表也有自测与提交，不能归因为缺少这两个工具或指令。Trace 914／920／926 的思考明确担心旧测试要求验证脚本托管服务，持续准备分段读取 `product.test.js` 核对；Trace 920 还提出写 `implementation.md` 后再读取，以恢复诊断额度。这是规则诱发绕行的证据，不是已完成自测的证据。

旧第 5 张卡的 goal 明确要求 `verify_product.py` 本地静态服务脚本，和当前 Dev Design「验证脚本只使用 Worker 传入 URL」冲突。无写入门禁把新的分段读取也算诊断额度，还可能拦截自测／提交；即使补齐工具说明，执行控制仍可能拒绝合理下一步。实际本样本没有自测／提交请求，因此不能声称这些请求已经被本样本门禁拦截。

开发助手候选方案，尚未获用户确认：在已有单元／切片交接流程中不再叠加五次非写动作门禁，保留重复读取、相同动作、无进展及总调用预算；自测／提交按自身版本门禁执行。显式提供当前验证执行契约，遇到旧卡要求托管服务时允许纠正违背系统契约的测试，保留实际业务断言，不修改批准产品需求。必须获得用户对执行控制调整的确认后才能实施。没有新增模型调用或代码改动。

限定编辑功能证据保留，replace 恢复与输入成本有改善迹象；自动返修仍未完成。原目标关闭审查的真实效果未验证，完整工作台需求及用户本人验收未完成。旧执行卡／测试中的脚本托管要求与现有规则冲突，属于待处理的上下文契约问题，本次仅记录、不改设计、不继续重置失败任务。
