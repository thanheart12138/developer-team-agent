## 1．要做什么

用户针对已有网站用自然语言说明问题。系统保留原需求和失败现场，调查、修改、自测、复验，最后提供修复后的网站及可检查的结果。普通修复默认不需要用户指定代码文件或理解内部阶段。

首版支持本项目已有任务中的原生 HTML／JavaScript、本地单用户网站，沿用 Node 测试、静态 HTTP 服务和 Python Playwright 验证。输入产物必须完整且在隔离任务工作区中；现有有效需求可定位，运行方式可确认。素材平台作为已有实例，不把首版称为任意软件返修工具。

首版从已有任务提交返修开始。外部仓库上传、任意目录导入、其他技术栈及数据迁移另行设计，不通过聊天中提供路径自动取得访问或执行权限。

## 2．为什么做

当前实际返修可以修好软件，却因责任卡范围和中间流程规划消耗大量上下文、卡在收尾。希望检验：一个主要执行会话是否能持续掌握目标，结合程序验证完成完整返修；在交付质量不下降后，再比较 Token 与干预成本。

## 3．用户流程

1. 用户选择已有网站，提交观察到的问题；可附已有复现和期望，但不要求提供技术方案。
2. 系统对照有效需求、真实产物和已有证据调查。能够确认的事项自主推进；缺少影响结果的产品决定时，只询问一个关键问题。
3. 在已批准目标内修实现及测试。修改产品行为、权限、数据规则或重要架构时，先提交变更方案并等待确认。
4. 执行 Agent 自测后明确提交。程序执行全量测试、服务检查、真实浏览器与独立目标核验；失败后继续修复。
5. 全部验证通过后，展示当前网站、修改内容、验证依据、成本和限制，进入等待验收。
6. 用户实际使用并决定通过或反馈新问题。独立复测通过不能自动代写用户验收。

## 4．用户可观察的信息

- 当前返修目标、进展、正在等待的事项。
- 当前软件是否可访问，以及本轮系统是否已完成验证。
- 已验证的修改与未解决问题。
- 明确停止原因：预算不足、等待决定、环境异常或验证未通过。
- 累计请求与 Token；不可获取的用量明确显示未知。

用户无需配置内部文件所有权、阶段名称或行为 ID。运行预算和执行环境由受控任务配置及明确授权确定。

## 5．怎么算成功

| 项目 | 成功标准 |
|---|---|
| 缺陷修复 | 原始问题在真实网站操作中消失，结果符合有效需求 |
| 回归 | 固定的原业务用例仍通过，错误后可继续正常使用 |
| 系统闭环 | 实现、自测、显式提交、全量测试、服务与浏览器验证、目标核验全部完成，正常进入待验收 |
| 用户参与 | 已明确事项不要求用户反复补充；重要产品决定仍由用户确认 |
| 恢复 | 中断后保留目标、原失败和累计成本，能够按可确认的执行状态继续 |
| 成本 | 完整成功与失败尝试都计入比较；完成质量优先，不用少 Token 但未交付充当收益 |

首轮真实验证采用普通缺陷、跨文件缺陷及中断恢复三个场景，并加入未针对性调试过的缺陷。每轮预先确认范围、外发数据和请求上限，不自动续费或扩预算。单次成功只证明该次结果，稳定性和成本优势待对应样本验证。
