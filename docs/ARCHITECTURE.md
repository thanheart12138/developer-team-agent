## 1．架构目标

2026-09-18 用户确认交接与责任路由，并调整为开发先自测：单元开发通过 run_unit_tests 请求程序固定的当前及已完成单元 Node 测试，取得真实结果后修复、重测；当前范围文件版本自测通过后才能通过 submit_unit_for_test 显式提交。程序拒绝未测、失败及过期提交，之后仍执行独立测试，不以文件存在或普通结束文本代替交接；连续无版本进展有提醒及有界停止。集成失败先只读诊断，结合需求、契约、代码和文件所有权决定责任单元，明确实现／测试错误只返回对应单元修复，跨单元实现问题按依赖协作修复；设计冲突、低置信或责任不明返回澄清。保留单 Worker、写入所有权、全量回归和浏览器门禁，不因修复放开全部文件或削弱测试预期。

2026-09-17 用户确认工具上下文更新：复用执行摘要账本，程序将当前开发循环的记录合并为按文件的有效读取／写入状态，核对当前版本，并提供必要失败、依赖测试状态和开发交接提示；不额外调用摘要模型，不自动附最近一批完整交互。模型按需获取的数据仍返回，重复全文仅保留一份。原始审计和恢复信息保持完整；不改变阶段推进、测试门禁或循环预算。

2026-09-17 用户确认增量：架构按职责划分模块，较大模块再按可独立验证的功能拆分；架构输出模块边界、依赖、数据所有权、公共接口及有序开发单元清单。先确定共享交互契约，再为每个模块或功能生成独立 Dev Design。单 Worker 串行执行每个单元的开发、程序测试、失败反馈和有界修复，通过后才推进；最终执行全量集成测试、HTTP 和真实浏览器完整流程验证。沿用现有七阶段、StepRun、Trace、检查点及预算，不新增数据库表。已生成的旧单份设计任务仍可沿用已有流程，新生成架构使用逐单元流程。允许按职责拆分文件，不因模块拆分自动授权持久化、依赖或新增业务功能。

本架构服务于首版计算器场景：用户通过本地网页提出软件需求，系统完成必要的需求确认、文档生成、代码开发、自动测试与修复，最终启动生成的软件并向用户提供本地访问地址。

v1 不追求支持任意软件、多用户、云端部署或并行开发，只验证一条最小但完整、可运行、可检查的交付链路；人工验收问题允许按最早失效产物进行有界跨阶段返工。

## 2．技术选择

- 前端：React
- 后端：Python + FastAPI
- 数据库：MySQL
- 模型：DeepSeek 与 Kimi 并存，按阶段固定路由；需求、架构和 Dev Design 使用 Kimi，开发及后续执行阶段使用 DeepSeek
- 运行环境：Windows 本地

Model Runtime 直接调用并封装两个兼容 Chat Completions 的 Provider，不引入第三方模型 SDK。Agent Loop 按当前 Step 固定选择 Provider；路由只影响模型传输层，不改变工具协议、状态机或任务数据。

## 4．组件职责

### 4.1 React 前端

- 接收用户的软件需求和追问回答。
- 通过 FastAPI 查询任务阶段、运行状态和待回答问题。
- 展示过程产物、失败信息以及最终生成软件的本地访问地址。
- v1 可通过轮询获取进度，不引入额外的实时通信组件。

### 4.2 FastAPI

- 接收前端请求并创建开发任务。
- 保存用户输入和追问回答。
- 向前端提供任务状态、待回答问题、文档产物和最终交付地址。
- 不在 API 请求进程中执行模型调用、代码生成、测试或软件启动。

### 4.3 MySQL

MySQL 同时承担运行状态持久化和 v1 轻量任务队列职责：

- 保存任务、当前阶段、运行状态和等待原因。
- 保存用户消息、模型调用和工具调用记录。
- 保存文件产物路径和最终软件访问地址。
- 支持单 Worker 领取待执行任务和未处理事件。
- 用户提交回答后，由 API 更新任务，使 Worker 能够恢复执行。

MySQL 中的运行记录是系统状态的权威来源。Task Workspace 中的 Markdown 消息文件属于过程快照或审计产物，不作为任务状态判断依据。

Trace 使用双层存储：MySQL 保存可增量查询的结构化索引，任务工作区保存完整请求和合并后的响应。流式片段仅通过系统临时目录的当前回答快照供前端展示，不写入 Trace 或永久原始事件数组；调用失败保留部分响应和错误。Trace 只用于展示、审计和调试，不参与 Task 或 StepRun 状态判断。

### 4.4 Worker Runtime

v1 严格运行单 Worker。Worker 从 MySQL 领取任务和事件并驱动后台长流程，不实现多 Worker 竞争、抢占或路由。模型调用、工具执行、测试和生成软件启动均在 Worker 中完成，不阻塞 FastAPI。

#### Agent Loop

Agent Loop 负责端到端流程编排：

1. 分析用户输入；存在阻塞性产品问题时进行多轮问答，期间不生成产品文档候选。
2. 模型确认无阻塞性问题后生成产品文档候选，由用户确认后写入正式产品文档。
3. 生成架构设计文档。
4. 架构正式化后，由受限 Scaffolder 生成可加载的代码框架：固定产品入口、模块接口、装配关系和逐模块待实现测试；程序验证结构和依赖关系，不实现业务规则。
5. 根据项目规模决定是否单独进行模块划分。
6. 生成项目或模块的 Dev Design。
7. 串行开发当前 v1；不相关模块并行开发留到后续版本。
8. 执行单模块测试、集成测试及必要的真实运行验证。
9. 测试失败时，在固定次数内修复并重新验证。
10. 验证通过后启动生成的软件，进入人工验收状态。

产品、架构和 Dev Design 默认单向推进；人工验收问题经分类后可以返回最早失效阶段。每个下游阶段执行前由 Transition Planner 对比新旧上游产物和当前下游产物，选择 `execute`、`revise`、`reuse` 或 `clarify`，不再因进入阶段就从头生成，也不因文件存在就跳过必要修改。开发阶段支持「开发→测试→失败修复→重新测试」局部闭环。单个 Step 最多调用模型 100 次，测试、启动或真实验证失败后最多返回开发阶段 3 轮。

如果需求确认或开发过程中出现无法由系统自行决定、且会明显影响最终产品结果的问题，Agent Loop 将任务置为等待用户状态；用户回答后从当前任务恢复。v1 不实现通用的向上返工机制。

#### Model Runtime

- 接收 Agent Loop 的模型请求。
- `product_docs`、`architecture_docs`、`dev_design` 固定使用 Kimi Code `kimi-for-coding`。
- `develop`、`test`、`start_product`、`verify_product` 以及测试失败后的返修固定使用 DeepSeek `deepseek-flash`。
- 同一个 Step 内的作者、评审和多轮问答始终使用该 Step 对应的同一个 Provider。
- 将模型输出封装成 Agent Loop 可处理的固定结构。
- 使用当前选中的同一个模型分别承担生成内容的 `author_agent` 和独立评审的 `reviewer_agent` 角色。
- Trace 记录实际 `provider` 和 `model`，但认证信息不得进入 Trace、日志或任务工作区。

当前版本不同时调用多个模型，不做投票或失败降级切换；阶段对应 Provider 调用失败时按现有失败策略保留证据。系统不记录 token usage，也不设置 token／金额预算。

#### Tool Runtime

- 接收 Agent Loop 的工具请求。
- 校验工具参数和任务工作区边界。
- 执行工具并返回固定结构的成功或失败结果。
- 记录工具调用，供 Agent Loop 判断下一步和保留验证证据。

v1 预定义三个工具：

- `read`：读取当前任务工作区内的文件，单次最多返回 100 KB。
- `write`：创建或原子覆盖文件。
- `exec`：在当前任务的 `product/` 目录中运行命令，支持普通执行及后台进程的启动、停止和状态检查。

所有文件工具只能访问当前任务工作区，`exec` 的工作目录固定为当前任务的 `product/`，模型不得指定其他工作目录。单条命令最长执行 60 秒，最多保留 100 KB 输出；后台进程必须记录并能停止。v1 不提供更新或删除工具，已有文件通过 `write` 的覆盖能力修改。

这些限制属于路径与进程级最小隔离，不是真正的安全沙箱。v1 不用于执行不可信需求，也不得接触真实个人数据或其他项目。

#### Task Workspace

每个任务使用独立工作区，避免多次运行之间相互覆盖：

```text
workspace/{task_id}/
├─ messages/    # 对话过程快照
├─ docs/        # 产品、架构、Dev Design 等文档
├─ evidence/    # 测试结果、运行记录和验证证据
├─ product/     # 生成的软件代码与运行目录
└─ traces/      # 不可变的模型、工具、校验和状态轨迹
```

Task Workspace 负责文件隔离和产物存储；任务状态、等待状态及产物索引仍以 MySQL 为准。

### 4.5 Trace 可视化链路

- Worker 在模型、工具、校验及状态边界追加 Trace。
- FastAPI 保存用户事件的 Trace，并提供索引增量查询与单条详情读取。
- React 继续使用轮询，按 Trace 序号追加动作，不刷新完整页面。
- 每条详情文件先在任务工作区原子写入，再创建 MySQL 索引；详情文件不可覆盖。
- Trace 写入失败不改变主任务业务状态，但必须产生运行告警，避免观测能力反向阻断交付链路。
- 已知敏感字段在持久化前过滤；认证头和密钥不进入 Trace payload。

界面采用左右双栏：左侧把用户消息、模型回答和 Trace 摘要按时间合并成连续信息流；右侧展示当前摘要对应的完整信息或文件内容。模型请求、原始返回、工具调用／结果及写入文件分别作为可点击摘要，详情按字段含义组织成人可读内容，不直接把整份 JSON 作为主界面。

模型 Provider 使用流式响应。Worker 限频更新临时的当前回答快照，前端轮询快照显示文本；调用结束清空快照，最终响应合并后形成 `model_response` Trace。刷新时可读取尚未过期的当前快照及已完成响应，不回放流式片段。

## 5．核心流程

### 5.1 创建与领取任务

1. 用户在 React 页面提交需求。
2. FastAPI 在 MySQL 创建待执行任务。
3. 单 Worker 轮询 MySQL 并领取该任务。
4. Worker 为任务创建独立 Task Workspace，随后启动 Agent Loop。

### 5.2 询问与恢复

1. Agent Loop 判断存在影响产品结果的重要问题。
2. Worker 将问题和等待原因写入 MySQL，并暂停该任务。
3. 前端通过 FastAPI 获得待回答问题。
4. 用户提交回答后，FastAPI 保存回答并使任务恢复为可执行状态。
5. Worker 再次领取任务，从已保存的当前阶段继续执行。

### 5.3 开发、测试与修复

1. Agent Loop 通过 Model Runtime 获取固定结构的开发或测试决策。
2. Agent Loop 通过 Tool Runtime 读写代码并执行命令。
3. 测试通过后进入交付流程。
4. 测试失败时保存证据，并在预算内生成修复、重新执行测试。
5. 超过次数或预算仍未通过时，任务进入明确的失败状态，不得伪装成已完成。

### 5.4 启动与交付

1. Worker 通过 `exec` 在动态选择的空闲端口启动生成的软件，并记录端口、进程 ID、启动命令和产品目录。
2. Worker 执行 HTTP 健康检查，并通过 Python Playwright 完成必要的真实浏览器功能验证。
3. 验证通过后，将本地访问地址和产物路径写入 MySQL。
4. FastAPI 向前端返回访问地址，任务进入等待人工验收状态。
5. 用户通过浏览器实际操作生成的软件并进行最终验收。

## 6．v1 边界

- 单用户、本地运行，不考虑权限体系和多用户并发。
- 严格单 Worker，不设计多 Worker 竞争、抢占或路由。
- Worker 串行开发模块，不做多 Agent 或模块并行调度。
- 不支持任务成功后的持续对话修改。
- 仅支持人工验收问题触发的有界跨阶段返工。
- 不支持模型供应商切换和动态工具注册。
- 不引入 Redis、Celery 或独立消息队列。
- 生成的软件固定使用原生 HTML、CSS、JavaScript，通过 Python 静态 HTTP 服务启动；逻辑使用 JavaScript 单元测试验证。
- 浏览器自动化固定使用 Python Playwright，端口动态选择。
- v1 采用路径与进程级最小隔离，不实现容器或虚拟机级安全沙箱。
- v1 不记录模型 usage，不设置 token 或金额预算。

## 7．开发设计

### 7.1 人工验收问题分流

- 用户只描述观察到的问题，不负责判断它属于需求、架构、Dev Design 还是实现。
- Worker 收到未通过的人工验收结果后，先由 Kimi 对照当前正式需求、架构、Dev Design、实现清单和验证证据进行分类，再由程序校验结构化结果并执行路由。
- 分类采用“最早失效产物”原则：改变产品行为回到 `product_docs`；需求不变但架构冲突回到 `architecture_docs`；架构成立但 Dev Design 冲突回到 `dev_design`；三份正式文档均支持而软件行为不符则回到 `develop`；证据不足则等待用户补充。
- 分类模型只能返回固定枚举和已有 Step，不能直接修改任务状态。分类请求、原始响应、引用依据、最终路由和用户原始反馈全部写入 Trace，并在任务工作区永久保存。
- 需求或设计返工使用新的 Step attempt 生成版本化候选与评审，再原子覆盖对应正式文档；旧候选、旧评审和 Trace 保留，不删除历史证据。
- 自动测试通过只表示当前测试集通过。收到人工问题后，在问题完成分类和对应返工前，不得再次宣称人工验收通过。

### 7.2 产品文档独立评审

- 产品门径确认信息足够后，Kimi Author 先生成产品 Draft；独立 Kimi Reviewer 对照全部用户消息、上一版正式需求、验收分类证据和本轮变更进行评审，按“阻塞问题、普通问题、建议”输出评审报告。
- 验收分类必须先把自然语言意见规范化为逐条变更契约，明确 `current_behavior`、`expected_behavior` 和可执行的 `acceptance_examples`；不能区分现状与期望时必须澄清，不能把用户描述的缺陷误写成新约束。
- 多条编号意见必须逐条解释和分类。初步分类后由独立 Consistency Validator 检查语用自洽性：如果某条被解释出的期望与现有正式需求相同，却无法解释用户为何把它作为问题提交，或总体分类遗漏了更早失效的条目，则必须返回澄清，禁止路由到开发。
- Product Author 根据 Draft 和 Review 生成候选版，必须解决阻塞问题；不得把普通问题或建议擅自升级为用户已确认需求。
- 候选版生成后由独立 Change Coverage Validator 逐条核对变更契约。任何条目未覆盖、覆盖方向相反或缺少验收示例时，程序禁止候选进入用户审批。
- 用户只审批经过评审修订的候选版。Draft、Review、候选版和最终正式文档分别保存，避免覆盖中间证据。

### 7.3 Transition Planner 与版本血缘

- 七个 Step 是可视化、权限和恢复边界，不是每次都必须重新执行的固定流水线。
- 进入架构、Dev Design 和开发前，Transition Planner 必须同时获得新旧上游正式产物、两者差异及当前下游正式产物，判断本轮应首次执行、增量修改、确认复用或等待澄清。
- 架构修订必须以旧架构为基线，只修改需求差异影响的章节；Dev Design 同理。模型不得只读取新版上游文档后推倒重来。
- 模型负责语义影响判断，程序负责固定枚举、允许跳转、文件存在、版本对应关系和完成门禁。模型自述“无需修改”不能替代版本证据。
- 每次决策保存输入版本、差异、受影响部分、保留部分、理由和动作；后续实现、测试和验证必须声明自己基于的上游版本。

### 7.4 模型调用技术降级

- Kimi 仍是需求、架构和 Dev Design 的首选模型；只有调用层技术失败时，当前逻辑调用才降级到 DeepSeek，阶段职责和输入上下文不变。
- 技术失败包括密钥／认证／限流／服务端错误、传输重试耗尽、响应结构或工具参数协议错误；业务评审不通过、低置信度、澄清、覆盖校验失败均不是降级条件。
- 降级不增加逻辑调用计数；Kimi 请求、失败、降级决定及 DeepSeek 请求／响应分别保存 Trace。DeepSeek 再失败时按原失败规则终止，不允许无限切换。

### 7.5 问答与产物上下文账本

- 一个问题与用户对该问题的回答是不可拆分的最小上下文单元；不得只抽取用户消息，使“是的”“保持一致”“忽略它”等回答失去指代对象。
- 任务工作区保存 `evidence/conversation-turns.json`。每轮记录问题／回答消息 ID、原文、状态、StepRun，以及该轮后续产生的工具动作和文件产物引用。
- 成功 `write` 后同时更新 `evidence/artifacts.json`，记录请求路径、工作区解析路径、文件名、创建／覆盖、字节数、SHA-256、工具调用 ID 和 StepRun；若存在当前已回答问答，则把产物引用关联回该问答。
- Context Builder 以当前正式文档、本轮验收变更契约和成对问答为工作上下文；完整原始 Trace 只用于审计。初始需求不得在已有新版正式文档时继续作为唯一主输入。

接口、数据、状态转换、模型及工具协议、异常恢复和验证流程见 `docs/DEV_DESIGN.md`。
