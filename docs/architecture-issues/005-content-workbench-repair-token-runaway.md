# 005：素材管理返修为何消耗 720 万 Token

日期：2026-09-20。状态：问题已定位，第一批流程与工具门禁已实施并完成机制回归；尚未用新的付费全链路证明成本下降。

## 问题与证据

素材管理真实 DeepSeek 运行共 184 次 HTTP，输入 6,861,504、输出 343,111、总计 7,204,615 Token，最终自动流程仍以 `unit_submission_required` 失败。生成产品的 6 个业务切片和 53 项 Node 测试实际已经完成，开发助手修正验证脚本后，真实 Chromium 全流程全部通过。

| 环节 | HTTP | Token | 占比 |
|---|---:|---:|---:|
| 产品、架构与首张切片 | 11 | 78,087 | 1.09% |
| 切片规划／重规划 | 30 | 850,860 | 11.81% |
| 六个业务切片开发 | 51 | 1,160,509 | 16.11% |
| 通用返修空转 | 68 | 3,879,213 | 53.84% |
| 定向浏览器返修 | 24 | 1,235,946 | 17.15% |

后期返修合计 5,115,159 Token，占 71.00%。调用 93～160 使用默认历史键和全产品上下文反复返修；调用 161～184 虽已缩小到 UI 所有者，但仍反复读取数百行文件、尝试整文件输出、触发输出截断并没有提交。

最终三个主要失败中，两个是验证脚本数量断言错误：流程创建 4 条素材、删除 1 条后应剩 3 条，脚本却断言 2 条；第三个用全新隔离 browser context 验证 localStorage 数据仍存在，违反浏览器隔离语义。流程没有先审查验证代码，而是持续要求开发 Agent 修改产品，扩大了错误方向上的消耗。

## 根因

1. 集成失败曾进入通用 Develop 返修，携带过大的代码与历史上下文，没有绑定入口文件所有者。
2. Step 的 100 次预算同时承担正常开发和返修，没有更小的返修专属预算。
3. 验证结果被默认当作产品事实，没有先检查测试脚本是否与其前序操作及浏览器语义一致。
4. 大文件读取和写入没有强制局部化，模型为修改少数行重复读取和输出整份文件。
5. 显式提交依赖模型主动调用；模型输出被截断后仍可继续消耗剩余 Step 预算。

## 已实施方案

- 集成失败按失败入口路由到拥有 `verify_product.py` 的已交付切片，只开放该切片的写权限；修改后立即复跑原浏览器验证。
- `read` 支持 `start_line`／`end_line`。单元开发读取超过 200 行的文件时只返回预览、总行数和局部读取提示。
- 新增唯一精确片段 `replace`，小范围返修不再整文件重写。
- `slice-developer/v6` 要求浏览器失败先核对数量变化和 localStorage context 语义，再判断验证脚本或产品代码责任。
- `model_tool_loop` 新增局部调用预算；业务切片集成返修按失败报告 SHA-256 指纹持久累计调用次数，Worker 恢复不会重置，即使 Develop 阶段还有剩余额度也不能继续空转。

## 2026-09-20：先修复旧失败驱动重复返修

针对调用 154～160 的 426,092 Token 小循环，浏览器验证现在同时写入 `verification-evidence.json`，记录人可读报告哈希、浏览器结果和当时全部行为相关产品文件哈希。进入普通返修或业务切片返修时，程序先比较当前哈希：一致才允许把失败报告交给模型；不一致表示报告已过期，程序直接使用当前 `verify_product.py` 和现有产品 URL 复跑 Playwright。

复跑通过时不调用模型，任务回到完整测试、启动和浏览器验证链路；复跑失败时，用本次真实输出和当前文件哈希替换旧报告，再进入责任切片返修。普通返修中的模型首次成功写入产品文件后立即结束当前模型循环，由程序复跑原失败验证，不再允许模型继续执行 Node 测试、读取或基于同一旧报告整文件重写。

新增回归覆盖失败证据保存版本、普通流程过期证据零模型复验、业务切片过期证据零模型复验、局部模型预算和跨恢复累计预算。完整 212 项测试通过。该结果证明调用 154～160 的同型机制路径已被阻断；真实模型成本收益仍须新的全链路评测。

## 2026-09-20：移除返修请求的全产品源码

旧运行调用 157 单次输入 60,416、输出 6,468、合计 66,884 Token；调用 154～160 合计 426,092 Token。该小循环每轮都携带 17 个产品文件，源码约 123,226 字符，同时可通过原始历史详情再次取回整文件写入内容。错误只涉及少数验证断言，但上下文成本按全产品规模重复支付。

普通返修和业务切片返修现在只传失败证据、验收／执行卡、文件路径与 SHA-256，不再预载 `current_product_files`。业务切片的读取权限进一步收窄到责任切片拥有的实现和测试文件；需要源码时必须围绕报错位置局部 `read`。返修同时移除 `get_tool_execution_detail`，保留文件变更摘要和模型调用摘要，避免历史整文件参数被重新注入。

回归测试直接检查最终模型请求：存在文件 manifest、没有源码快照、没有原始历史详情工具；同时检查普通返修快照随修改刷新，业务切片只拥有责任范围的读取权限。完整 213 项测试通过。该改动消除了已定位的固定输入来源，但真实 Token 降幅仍以新的同需求付费全链路为准。

## 2026-09-20：事务式返修

返修不再把剩余调用额度交给模型自由循环。同一失败证据最多两次调用：模型可先局部读取诊断，随后必须实际修改；首次文件变化立即结束模型循环，由程序复跑原 Node 或浏览器验证。两次调用后没有文件变化立即失败，相同证据不再重试。

程序复验产生不同失败输出时，才允许第二轮两次调用；整个业务切片返修跨 Worker 累计最多四次调用。第二轮仍失败即停止。普通返修同步取消三次无变化纠正，收敛为最多两轮、每轮两次调用。这样直接阻断“模型文字声明完成但文件未变”和“同一报告重复诊断”两类空转。

## 验证标准与未完成项

机制回归必须证明：默认模型循环仍保留原 Step 预算；指定局部预算后准确停止；业务切片返修固定传入 8 次预算；大文件读取只返回预览且可按行取片段；现有流程测试全部通过。

新的真实评测必须从空工作区运行同一素材管理需求，并同时满足：自动流程进入人工验收、没有开发助手修改生成产物、Node 与 Chromium 全部通过、单份失败证据不超过 2 次且整个返修不超过 4 次模型调用、总 Token 显著低于 7,204,615。未完成该评测前，只能说明失控路径已被门禁限制，不能宣称成本优化成功。
