# 006：测试修复犹豫、重复读取与修改后强制复测

日期：2026-09-20。状态：最小测试返修闭环已通过；普通开发重复读取进一步采用独立受限实现，取得一个真实 materials 局部成功样本。完整页面保存未通过，稳定性与全链路交付未验证。

## 问题发现

事务式集成返修实施后，从空工作区重新运行真实 DeepSeek 素材管理任务。流程在第二张 `topics-management` 业务切片失败，状态为 `failed / develop / unit_development_no_progress`。整轮 35 次 HTTP、625,466 Token，其中第二张切片 17 次、418,147 Token。

局部 Node 自测只有一个失败：`tasks.test.js` 先通过 `tasks.configureInjectedCallbacks({ getTopicById: topics.getTopic })` 装配被测模块，随后却调用 `topics.configureInjectedCallbacks({ getTopicById: () => undefined })`，再期望 `tasks.getSourceTopic` 返回 `undefined`。修改 topics 自己的回调不会改变 tasks 已保存的回调，因此测试夹具没有正确表达“tasks 通过注入回调实时查询”的 acceptance。

DeepSeek 已在最后一次响应中明确判断：错误在测试的回调对象，正确修改应把 `topics.configureInjectedCallbacks` 改为 `tasks.configureInjectedCallbacks`。但它没有执行 `replace`，而是继续读取同一失败片段，最终耗尽无进展额度。

## 原因判断及修正

最初判断是模型担心改错，所以重复确认。继续核对模型原文后，这一解释证据不足。模型写道测试文件“asserts intent”并再次考虑是否能修改，说明更直接的原因是提示词只强调“不得降低、删除或绕过测试”，没有明确区分：

- 修正错误的测试实现，使其忠实表达 acceptance；
- 为迎合错误产品实现而削弱断言。

流程同时存在三个放大因素：

1. 自测失败后仍处于普通开发工具循环，没有强制从诊断转到修改。
2. 重复工具门禁只比较完整参数；模型改变行号或 description 就能重复读取同一语义区域。
3. 无进展门禁允许 8 个无文件变化批次，足以让约 30K 输入 Token 的大上下文反复发送。

因此最终判断是：**提示词造成修改测试的权限歧义，程序又允许诊断完成后继续读取；两者共同导致空转。**

## 决策

用户决定同时修复提示词和程序约束：

1. 提示词明确授权修正错误测试实现，只要 acceptance 业务语义和覆盖强度不降低。
2. 自测失败后，已读取失败区域不得在文件未变化时再次读取重叠范围。
3. 失败修复一旦产生实际修改，下一模型批次必须复测，不能重新读取或继续诊断。
4. 不再为每次提示词调整运行完整全链路；先用低成本决策回放，再用最小局部工具行为测试。

该夹具还暴露：失败来自 `unit_test_feedback`，不在当前工具历史里，最初的重叠读取门禁没有识别这种恢复证据。

## 最终方案

### 提示词 v7

`slice-developer/v7` 明确规定：测试文件不是不可修改的规格原文；测试没有表达 `card.acceptance` 时，可以修正错误回调对象、夹具装配、数量计算和环境假设。模型必须保持业务语义及覆盖强度，定位后立即修改，不得继续读取已覆盖的失败区域。

### 失败后重叠读取门禁

Runtime 识别最近失败自测之后成功读取的文件和闭区间。文件未发生修改时，后续读取同一文件的区间只要与此前区间重叠，就返回 `self_test_repeated_read_requires_change`。改变 description、缩小或平移行号不能绕过；读取尚未覆盖的必要依赖仍然允许。成功修改后该读取门禁解除。

### 修改后强制复测

Runtime 同时识别当前工具历史中的失败 `run_unit_tests` 和版本匹配的 `unit_test_feedback.passed=false`。失败修复中的某批 `write`／`replace` 成功后：

- 同一批可以完成同一根因的多个相关修改；
- 下一模型批次只允许 `run_unit_tests`；
- `read`、继续诊断、提交或跨批修改返回 `unit_change_requires_self_test`；
- 复测失败后重新开放必要诊断；
- 复测通过后进入原提交门禁。

## 最小返修夹具阶段的结论与边界

问题已在最小真实模型工具闭环中解决：提示词降低犹豫，程序门禁保证旧提示词或偶发模型行为不能在修改后继续诊断。该组合优于只依赖模型自律，也优于单纯缩短总调用预算。

尚未重新运行完整素材管理全链路，因此不能声称第二张切片或整个产品已经交付，也不能把局部节省外推为全链路 Token 降幅。第二张卡同时包含四个模块导致单次输入接近 30K Token，是独立的切片范围问题；后续已通过 `slice-planner` v5、Runtime 重复模块校验和 Developer 当前卡文件预载进行机制修复，真实成本仍待验证。

## 后续：普通开发推进违约后的对话切换

### 新证据推翻的假设

将门禁扩展到普通开发后，五个 materials 局部样本仍全部失败，共 42 次、396,835 Token。ToolResult 和下一请求的显式约束没有稳定让模型执行写入／自测。因此此前“程序门禁可以让模型改动后自主复测”的局部经验不能直接推广到普通开发，也不能认为拒绝工具等于切换执行状态。

### 用户确认的控制流与取舍

不再继续同类反馈微调。首次完整重复读取被拒后，下一批首次违反推进约束即结束旧对话；以 Runtime 校验的接口—文件映射、当前 owned_files 及只读依赖全文开启新历史。新调用只允许写入、替换或重规划，一个写入批次后直接由 Runtime 自测，通过后调用原提交校验，再独立回归。切换与最多四次实现／修复额度持久化，恢复保持同一尝试，依赖缺失或证据过期明确停止。

相比继续旧对话，这会增加一次完整依赖快照，但消除反复确认和等待模型主动测试／提交的控制权空缺。相比直接取消测试或放宽文件范围，它保留相同验收和所有权。没有把测试通过等同用户验收。

### 实施、验证与局限

实现位于 `slice_workflow.py`、`worker.py` 和新增独立 `slice-implementer/v1`；新增 17 项机制回归，完整 241 项通过。用户授权的唯一局部 DeepSeek 样本中，旧对话在第五个有效响应首次推进违约时终止；新调用第一次写实现，Runtime 因八个 todo 拒绝提交，第二次写真实测试后自测、提交及独立 Node 均通过。只修改两个拥有文件，无人工补写产物。

七次有效响应共 76,859 Token，切换后两次占 28,939；另三次连接失败计入总请求 10／12。没有重置预算或追加第二个模型样本。该样本比此前最后一轮失败多用 2,258 Token，因此证据支持“完成度改善”，不支持稳定降耗结论。

独立五组 Node 验收及真实浏览器内模块错误恢复、搜索、刷新持久化通过。实际整页保存仍失败，未实现 UI 的公共依赖路径 404；完整软件未交付、未验收。原五轮失败、审批拒绝及核查后续跑、当前样本和验证边界完整保存在 [独立实现验证](../evidence/materials-control-switch-validation.md) 。


### 2026-09-20：剩余切片续跑暴露响应截断恢复缺口

用户明确批准 DeepSeek 外发范围后新增 16 次请求、302,495 Token。任务／选题和看板／页面均发生旧对话终止及独立实现切换；前者两次实现后累计 40 项自测及独立回归通过，说明切换机制并未失效。后者第三次受限调用达到 8,192 输出 tokens，finish_reason=length，工具 JSON 不完整，未执行该批写入。

当前每批 model_tool_loop 的 max_calls=1 与协议失败后 continue 的恢复路径相冲突：下一轮无法进入，最终错误变成 model_loop_call_budget_exceeded，外层直接记为 failed。实际仅用了三次受限实现，四次上限及本轮六十次 HTTP 均未耗尽。独立 Node 为 40 pass、1 fail、9 todo；看板测试本身还有非 async 函数使用 await 的语法错误，完整 UI 未验证。

开发助手建议：保留原始失败类别，明确截断批次能否在既有四次预算内进入下一次独立修复，并约束输出规模；不能只增加总调用上限。该恢复策略尚待用户决定，未改变设计或实现，未追加付费重试。详见 [续跑证据](../evidence/content-workbench-continuation-validation.md) 。

### 2026-09-20：整文件输出截断与局部替换决策

#### 问题与证据

上述失败响应用 write 重写两份测试：看板测试参数约 8,547 字符，页面测试参数已输出约 22,419 字符但未结束。代码、中文注释和工具 JSON 都占输出额度。实际请求没有设置 DeepSeek 输出上限；响应在 completion_tokens=8192 时返回 finish_reason=length，不能据此断言 8,192 是模型硬上限还是服务端默认限制。

受限执行器当时已经提供 replace(path, old, new)，工具要求 old 在文件内唯一精确匹配；v1 也有简短的「局部修改优先 replace」提示。因此问题不是缺少工具，而是模型选择整文件重写，提示不足以约束修改方式，再叠加前述协议错误恢复缺口。旧 Developer 对话已成功终止，不能把这次失败归因于对话切换未生效。

#### 授权、技术决策与取舍

用户要求：没有局部替换工具就提供；已有则强化优先局部替换，或考虑只给 replace。开发助手在该授权范围内采用提示词强化方案，新增并激活不可变版本 `slice-implementer/v2`，保留 v1 失败证据。

- 已有文件的语法、import、函数及断言修复优先最小精确片段 replace；不输出无关代码，不用整文件 old/new 变相重写。同文件多次替换按顺序匹配最新内容。
- write 保留给新文件或绝大部分内容仍待首次实现的骨架。未采用 replace-only：它不能创建新文件，对整体骨架替换还需同时输出旧文和新文，不一定减少输出量。
- 保留原工具权限、四次实现预算、自测及提交门禁。该方案是模型行为引导，不是程序强制禁用 write，也不能保证大规模首次实现不再截断。
- 未采用提高总调用预算或调整 Provider 输出上限。协议错误分类及截断后在原预算内恢复属于另一项待确认控制流决定，本次没有实施。

#### 验证方法、结果与限制

注册及控制流相关 21 项机制测试通过。用户另行要求局部真实测试后，复制上次失败产品，对原第 16 次请求仅替换 v1 为 v2，保留其他上下文、工具定义与模型参数；通过正式 DeepSeekRuntime 解析、RestrictedImplementationTools 执行，并独立运行 Node。该单批回放未续跑原任务、未重置其计数，也没有人工补生成代码。

| 指标 | 原 v1 失败响应 | v2 局部回放 |
|---|---|---|
| 输出 tokens | 8,192，截断 | 860，完整 |
| 工具动作 | 两个整文件 write 的参数，第二个未完成，整批未执行 | 两次 replace，均执行成功 |
| 本轮实际修复 | 无新写入落盘 | 看板测试的依赖引用及非法 await |
| 独立 Node | 40 pass、1 fail、9 todo | 45 pass、0 fail、9 todo |

v2 本次一次请求、无重试，输入 30,327／输出 860／合计 31,187 tokens；只改看板测试，原五项测试断言保留，未删除或跳过。原输入所含失败是有效的，修复后五项看板测试通过。

当前结论是「一个真实局部样本中，模型采用局部替换，修复有效且未截断」。本次没有补 UI 九项 todo，完成范围比原响应尝试的范围小，因此不能把输出减少解释为同等交付量的纯效率提升，更不能声称完整切片完成、稳定降耗或截断问题彻底解决。原任务仍失败，完整页面未验收。

详细证据见 [续跑及局部回放记录](../evidence/content-workbench-continuation-validation.md) 。原始请求、响应、工具结果和 Node 日志位于 `/private/tmp/replace-prompt-v2-local-20260920`，入口为 `/private/tmp/replace_prompt_local_validation.py`；临时目录可能被清理，本记录保留关键决策与结果。
