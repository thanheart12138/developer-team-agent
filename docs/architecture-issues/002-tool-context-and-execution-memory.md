# 002：工具上下文压缩与执行记忆的取舍

日期：2026-09-17。状态：有效状态投影已实现并验证，稳定成本优势未证明，完整真实自主交付未通过。

## 问题与目标

工具结果包含读取全文、写入参数和命令输出；长期携带完整交互容易增长上下文。但只提供当前代码又可能失去「已做过什么」的进度。目标是降低总任务消耗，同时保留推进、故障定位和恢复需要的记忆，完整审计证据仍能按需取回。

用户先提出逐工具摘要及历史查询，随后明确要求对照只携带当前必要内容，最终确认复用已有摘要账本，聚合为当前有效状态。架构关键是区分持久审计、恢复检查点和模型上下文，三者不使用同一份不断累积的全文。

## 解决过程

1. 建立逐工具账本，工具关联父逻辑模型调用，记录目的、结果、文件 SHA-256 和 Trace 引用。重试沿用逻辑调用 ID，重复登记幂等。
2. 增加当前任务内三个查询：文件修改历史、某逻辑调用的批次摘要、某摘要的原始执行详情。历史查询不重新执行工具。
3. 首个投影保留最近一批完整交互和最近 20 条较早摘要，未解决失败与执行版本另列。缺摘要的旧检查点不静默丢失结果。
4. 隔离对照取消自动完整历史和摘要，只提供当前设计、代码、失败反馈及明确请求的读取／查询数据。第一变体发现读取全文与快照重复，保留结果后去重再测。
5. 去重后仍出现反复读取，文件齐备但模型不结束开发，直到单阶段 100 次上限。当前代码不足以稳定替代执行进度，是行为证据支持的判断，不是可观测的模型内部心理解释。
6. 最终复用账本按文件合并最新读／写，核对当前版本和读取完整性。最近更新 20 个文件状态，不随重复操作累积。当前读取与快照重复则返回引用；另附缺文件、已完成单元测试版本和交接提示。

## 方案取舍与确认

| 方案 | 价值 | 风险／当前决定 |
|---|---|---|
| 累积完整工具历史 | 调用与结果配对明确 | 长结果反复发送，保留作为审计而非默认全部模型上下文 |
| 最近完整批次＋较早逐工具摘要 | 保留刚完成操作及历史线索 | 同文件重复读取仍增加摘要，固定设计样本成本目前最好，不能忽视 |
| 仅当前设计、文件与按需数据 | 每轮不用自动历史 | 真实样本大量重复读取，暂不采用为正式策略 |
| 当前有效状态＋按需原始数据 | 保留进度，合并重复操作，版本可核对 | 用户确认实施；测试出现另一个返修问题，成本优势仍待对照 |

不增加模型摘要调用，程序按实际账本生成；不把「已读取」误写为「已完成语义审查」，不把「文件存在」误写为「测试通过」。更早记录仍可查询。当前不会仅因文件存在就自动结束开发，阶段控制问题与有效状态提供分开处理。

## 固定设计对照与消耗

同一合成 math／ui 需求和三单元预置设计，从空产品开始；普通 pytest 不触发付费调用。下表是各样本实际 HTTP 及完整 usage，不是单次模型输入长度。

| 投影 | HTTP 次数 | 输入 Token | 输出 Token | 总 Token | 最终状态 |
|---|---:|---:|---:|---:|---|
| 最近完整批次＋较早摘要 | 13 | 55,500 | 7,818 | 63,318 | waiting_acceptance |
| 仅当前内容，存在重复全文 | 65 | 433,538 | 14,329 | 447,867 | waiting_acceptance |
| 仅当前内容，已去重 | 100 | 552,716 | 18,450 | 571,166 | failed／调用上限 |
| 当前有效状态摘要 | 26 | 109,888 | 10,936 | 120,824 | waiting_user／返修范围澄清 |

原 13 次样本在前 10 次时碰到共用测试预算，恢复后追加 3 次。其余样本代码、测试数量、随机输出和结束状态不同，不能算严格 A/B；不能将倍数当成通用节省比例。第一变体的重复全文是额外干扰，已明确排除作为直接因果依据。

去重无记忆样本共 read 208 次、write 9 次；有效状态样本前 22 次完成单元开发、测试及最终 Node 23 项，后 4 次在集成失败返修中等待澄清。不能直接把「26 次」全部当作纯开发成本。

## 机制及真实行为验证

142 项机制回归通过，新增 5 项验证读取合并、当前版本失效、截断／缺失文件、按需数据不累积、快照去重及交接状态。恢复窗口保留原证据，不重复执行已完成副作用。

实际发送体逐份核对：有效状态样本无历史 assistant/tool 消息，重复操作按文件合并，按需读取无重复全文。仅当前内容与有效状态产物均独立 Chromium 18 组通过，不能代替各自自动流程完成。首批工具摘要真实大任务曾调用 83 次仍未交付，其中完整 usage 81 份；它的任务与输出配置不同，不与上表相加或直接比较方案效率。

## 当前决定、结果与待办

用户确认的有效状态投影已加载正式 Worker。当前保留版本和执行进度，压缩历史重复全文，不退回完全无记忆，也不声称比原 13 次方案更省。

已发现阶段控制仍等待模型停止工具调用，重复动作保护只识别连续完全相同参数，description 变化及交替读取可能不被识别。这些是代码依据；它们对总循环的具体贡献未通过独立故障注入分离。自动测试交接与无进展检测是待讨论方向，未在本轮暗中加入。

2026-09-18 已确认并实现 003 的责任诊断及 [004 的显式提交与无进展停止](004-unit-handoff-and-progress-control.md) ，机制验证通过，真实脚本故障夹具出现一次修复成功及一次无进展失败，从零开发也未完成。当前仍未执行不同记忆方案的严格控制变量对照，不能将路由／交接变化后的成本归因于摘要投影。

2026-09-24 用户决定开启 DeepSeek thinking。官方工具协议要求后续带工具请求回传前轮完整 `reasoning_content`；原有效状态投影会丢弃已记账工具轮次，不能直接满足协议。本次保留用户可见的文件状态摘要，同时为 DeepSeek API 单独续传当前执行循环的原始 assistant／tool 轮次及思考；同一次响应的多个工具调用合并到一条 assistant 消息。机制回归 215 项通过，隔离同断点真实 DeepSeek 3 次请求完成测试夹具返修，Node 23 项通过，输入 66,044／输出 3,945 Token。此举增加协议续传上下文，稳定成本收益未知；旧检查点无思考内容不能凭空重建。完整证据见 [DeepSeek thinking 断点实验](../evidence/deepseek-thinking-checkpoint-20260924.md) 。正式 Worker 因运行中任务无法核查而未重启；完整产品交付未验证。
