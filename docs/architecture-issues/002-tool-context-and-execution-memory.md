## 问题与目标

2026-09-30 后续真实证据：按修正实现从已修编辑产物隔离续测，20 次共 1,167,148 Token，低于前次 3,484,768，但起点与操作不同，不能做严格成本归因。模型仍多次读取且未自测／交接，故上下文体积下降未解决流程收敛；没有继续加预算。详见 [有界交接续测](../evidence/repair-objectives-completion-deepseek-20260930.md) 。

2026-09-30 更新：真实隔离返修用满 20 HTTP／3,484,768 Token，功能限定验收通过但未交接。核对请求发现每轮 current_product_files 约 26 万字符，非目标账本占主要体积。用户确认改为单元／切片按需读正文；保留哈希清单、失败反馈和 DeepSeek 所需历史，正文已省略可补读，仍保留相同版本范围内容时继续去重。另修复无写入门禁达到阈值后拒绝 replace 的恢复动作，失败替换不重置计数。239 项回归通过，离线 context 289,586→28,034 字符；未新增真实调用，不能声称总 Token 同比例减少或交接成功。详见 [机制修正验证](../evidence/repair-context-and-replace-guard-validation-20260930.md) 。

工具结果包含读取全文、写入参数和命令输出；长期携带完整交互容易增长上下文。但只提供当前代码又可能失去「已做过什么」的进度。目标是降低总任务消耗，同时保留推进、故障定位和恢复需要的记忆，完整审计证据仍能按需取回。

用户先提出逐工具摘要及历史查询，随后明确要求对照只携带当前必要内容，最终确认复用已有摘要账本，聚合为当前有效状态。架构关键是区分持久审计、恢复检查点和模型上下文，三者不使用同一份不断累积的全文。

## 解决过程

1. 建立逐工具账本，工具关联父逻辑模型调用，记录目的、结果、文件 SHA-256 和 Trace 引用。重试沿用逻辑调用 ID，重复登记幂等。
2. 增加当前任务内三个查询：文件修改历史、某逻辑调用的批次摘要、某摘要的原始执行详情。历史查询不重新执行工具。
3. 首个投影保留最近一批完整交互和最近 20 条较早摘要，未解决失败与执行版本另列。缺摘要的旧检查点不静默丢失结果。
4. 隔离对照取消自动完整历史和摘要，只提供当前设计、代码、失败反馈及明确请求的读取／查询数据。第一变体发现读取全文与快照重复，保留结果后去重再测。
5. 去重后仍出现反复读取，文件齐备但模型不结束开发，直到单阶段 100 次上限。当前代码不足以稳定替代执行进度，是行为证据支持的判断，不是可观测的模型内部心理解释。
6. 最终复用账本按文件合并最新读／写，核对当前版本和读取完整性。最近更新 20 个文件状态，不随重复操作累积。当前读取与快照重复则返回引用；另附缺文件、已完成单元测试版本和交接提示。

## 方案取舍与确认

| 方案 | 价值 | 风险／当前决定 |
|---|---|---|
| 累积完整工具历史 | 调用与结果配对明确 | 长结果反复发送，保留作为审计而非默认全部模型上下文 |
| 最近完整批次＋较早逐工具摘要 | 保留刚完成操作及历史线索 | 同文件重复读取仍增加摘要，固定设计样本成本目前最好，不能忽视 |
| 仅当前设计、文件与按需数据 | 每轮不用自动历史 | 真实样本大量重复读取，暂不采用为正式策略 |
| 当前有效状态＋按需原始数据 | 保留进度，合并重复操作，版本可核对 | 用户确认实施；测试出现另一个返修问题，成本优势仍待对照 |

不增加模型摘要调用，程序按实际账本生成；不把「已读取」误写为「已完成语义审查」，不把「文件存在」误写为「测试通过」。更早记录仍可查询。当前不会仅因文件存在就自动结束开发，阶段控制问题与有效状态提供分开处理。
