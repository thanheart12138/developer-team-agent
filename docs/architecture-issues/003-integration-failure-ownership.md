# 003：集成失败如何回到正确的开发单元

建立：2026-09-17，更新：2026-09-27。当前状态：用户确认的只读诊断和责任路由已实现；机制及真实单模块测试脚本故障样本通过，真实跨单元修复及稳定成功率未验证，用户未验收。以下初次分析与未实施状态保留为历史，最新进展见末节。

## 问题与触发证据

逐单元开发按文件所有权限制模型写入。局部测试失败有明确当前单元，但最终全量测试或浏览器验证跨越多个单元。现有全局失败返修会重新访问已完成单元，并将全局反馈交给它们，而没有先判定责任归属。

有效状态真实探针完成三单元、Node 23 项及启动；生成浏览器脚本失败后，square 数学单元收到 UI／验证脚本问题。它无权修改这些文件，返回 BLOCKED 并等待设计澄清。所有权保护生效，却与全局返修方式冲突。

触发 bug 是 verify_product.py 先把 B 设为 1000，恢复用例只把 A 改为 4，却期待平方为 16；实际 (4+1000)^2=1008016。此脚本 bug 不单独建档；这里记录的是「跨单元失败没有责任路由」的架构问题。普通脚本错误不应自动升级成用户必须重新决定架构的阻塞。

## 解决过程与当前证据

1. 保留失败报告和生成代码，未人工修补脚本或代答澄清。
2. 核对脚本输入与断言，确认具体失败属于验证代码输入／预期不一致，不能据此称数学结果错误。
3. 检查模块所有权：UI 持有 UI 实现及 verify_product.py，square 只持有数学实现与测试；square 不能越权修复该失败。
4. 用真实 Chromium 独立操作确认需求 18 组通过，页面异常 0；独立结果用于诊断，不改变原 waiting_user 状态，也不替代系统验证通过。
5. 区分直接缺陷和架构根因：局部测试门禁存在，缺少的是全局失败到责任单元的有效交接。当前尚未形成用户确认的修复设计。

## 目标与候选取舍

目标：在保持文件所有权、测试预期和有界预算的前提下，让实现缺陷返回责任单元；只有确认契约／设计缺口时才交用户决定。下面均为开发助手分析，未获实施确认。

| 候选方案 | 收益 | 代价／风险 |
|---|---|---|
| 所有单元顺序重跑并接收同一失败 | 不增加定位组件 | 当前机制已暴露无关模块被阻塞，费用增加 |
| 依报告中的文件路径匹配所有者 | 简单、可复核，适合明确脚本异常 | 堆栈出现位置不一定是实际根因，不能一律直接授权修复 |
| 程序提供文件归属，受约束模型定位责任 | 可处理实现／测试／跨模块契约不同原因 | 增加诊断调用、置信度和错误归因处理，需设计与故障验证 |
| 临时放开全部文件让模型统一修复 | 避免单元越权阻塞 | 破坏模块边界，可能修改依赖或削弱测试，不建议直接放开 |

优先讨论路径归属作为确定线索，不确定时再有界诊断；这只是建议，不是已采用的方案。谁可读取什么证据、可修哪些单元、跨模块修复顺序和复验范围仍待确认。

## 方案测试与最终状态

已有测试是复现和诊断，不是新路由验证：真实探针共 26 次／120,824 Token，包含前 22 次开发和后 4 次全局返修。square 返回范围澄清，证明所有权保护没有被绕过；不能证明架构缺口真的需要用户回答。

尚未执行候选方案测试。确认方案后需要覆盖：明确验证脚本错误、明确单模块实现错误、跨模块接口不一致、无法确定责任；检查修复仅写允许文件，保留需求预期，测试有效版本，复跑受影响单元和最终集成。测试成本与成功率待测，不填写虚构结果。

初次记录时正式机制没有路由修复；原隔离任务保持 waiting_user／dev_design。不得将后续新夹具成功改写为原任务已通过。

## 2026-09-18：确认、实现与复测

用户确认显式交接及受约束只读诊断方案。诊断提供实际失败、正式需求、契约、当前代码和文件归属，不允许工具写入。程序校验分类、置信度至少 0.8、非空依据及修复目标、责任单元存在／不重复，单模块只允许一个目标，跨单元至少两个。无效或不明确结果回澄清，不根据堆栈直接放开权限；诊断证据按失败、设计和文件版本绑定恢复。

只有责任单元接收全局反馈，其他当前版本一致的已通过单元复用；依赖变化正常复验，最后仍执行全量和浏览器测试。当前机制回归包含错误脚本、实现错误、跨单元、契约冲突、低置信和非法归属。完整后端 164 项通过，其中本轮新增 22 项涵盖本问题及 004。

真实测试从已验证产物复制的隔离夹具开始，不冒充从零自主开发。先 Node／浏览器通过，再在验证入口前注入违反已确认需求的错误断言。DeepSeek 诊断 test_script_error／ui／置信度 0.97，最终成功样本 7 次／78,234 Token：只写 verify_product.py，提交后 Node 43 项和系统 Chromium 通过，waiting_acceptance；修复后脚本与注入前字节完全一致，数学文件未被模型改写。独立 Chromium 18 组通过、页面异常 0。

失败过程保留：首次注入放在 sys.exit 后，故障不可达，0 次模型调用，不作为返修成功；修正注入后的第一样本正确定位并修改脚本，但没提交，16 次／183,824 Token 后无进展停止。将无进展提醒加入系统指令后新建夹具复测成功，但该成功样本未达到提醒阈值，不能将成功归因于提示调整。单样本也不能证明稳定成功率。

当前只有真实单模块脚本错误路由的成功证据，其他类别为 Fake／真实工具机制验证。原 waiting_user 任务未续跑。详情见 [交接与路由验证](../evidence/unit-handoff-repair-validation.md) 。

## 2026-09-27：验收缺陷与脚本失败的目标保持

隔离内容工作台的独立 Chrome 验收发现已有素材没有编辑入口；批准需求同时要求编辑素材和选题。验收规划器在补清 JSON 行动契约并重述既有复现后，实际读取代码，分类为 `implementation_defect`／`modify_code`。负责最终页面装配的切片本来拥有素材、选题视图及 `verify_product.py`，不存在文件权限不足。

返修先大量修改 `verify_product.py`。该脚本自行启动 HTTP 服务且在缺少 Playwright 自带 Chromium 时输出 `[skip]`；修正 Worker 的跳过与脚本预检门禁后，最新报告持续指向验证脚本。后续模型仍主要修脚本与说明，原验收缺陷没有作为独立未闭合条件约束返修完成。最终累计 128 次 HTTP／12,026,798 已报告 Token，任务 `failed / develop / unit_development_no_progress`，独立浏览器仍报 `material_edit_entry_missing`。这说明「路由到有权限的切片」本身不足以保证原始验收目标被保留；也不能将模型未完成单独归因为能力不足。

已实现的局部机制修复：`[skip]` 大小写均不通过、自建 HTTP 服务脚本预检、返修复验共用预检、最新复验失败进入剩余返修预算。未解决的架构决定：验收缺陷与随后出现的验证脚本错误如何分别记账、反馈和核销；不能因修好了一个报告或模型自称完成，就抹去另一个未验证目标。该决定待用户设计确认。本次详细过程见 [编辑验收续测](../evidence/content-workbench-edit-acceptance-continuation-20260927.md) 。

## 2026-09-28：产品行为到切片证据的覆盖门禁

进一步核对旧 Trace：第五张卡生成请求确实包含完整正式产品需求，但卡片八条验收没有页面编辑；程序原先只校验卡片自身字段和接口映射。完成报告把仓储 `update` 断言当成「编辑」已覆盖，暴露产品行为与验证层级没有独立对应关系。用户确认先试系统内部行为标准，且明确产品文档不能增加面向技术人员的操作验证字段。

离线阶段已实现内部标准提取与独立审查、原文引用校验、卡片行为 ID、完成前独立覆盖审查及代码变化后的审查失效。旧产物只读回放得到「修改笔记」A001 无切片归属；Fake 模型＋真实 Runtime 与后端 228 项测试验证门禁会退回规划，浏览器成功也不能覆盖行为审查失败。当时尚无真实模型提取／审查测试，不能声称当前缺陷已由 DeepSeek 修复或新机制能保证语义无遗漏。原验收缺陷与脚本错误的长期独立记账仍未设计确认；详见 [离线验证](../evidence/acceptance-standard-offline-validation-20260928.md) 。
