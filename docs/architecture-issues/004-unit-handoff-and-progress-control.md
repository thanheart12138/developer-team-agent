# 004：开发如何交接测试，以及何时停止无进展调用

建立：2026-09-18，更新：2026-09-27。状态：用户确认开发先自测后提交，调整已实现并通过机制验证；已有一个真实自测故障修复与交接成功样本，稳定性及从零交付未验证，原失败保留，用户未验收。下述先提交后测试为历史方案，当前有效方案见末节。

## 问题与证据

原流程等模型不再提出工具调用才开始程序测试。仅当前内容的真实去重样本生成文件齐备后仍反复读取，100 次／571,166 Token 到调用上限。即使产物独立操作通过，自动流程也无法收尾。

上下文解决「模型看到什么」，交接和进展控制解决「程序何时接手、何时停止」。本问题从 002 单列，避免把流程控制全部归因于摘要策略。

## 目标、取舍与用户决定

| 候选 | 收益 | 取舍 |
|---|---|---|
| 等自然结束文本 | 最简单 | 模型反复工具调用时无法交接，不继续作为新单元正常完成方式 |
| 文件齐备自动进入测试 | 减少模型决策 | 文件可能未写完，不能仅凭存在判定开发就绪，不采用 |
| 显式 submit_unit_for_test | 交接可审计、可绑定版本、与测试通过分离 | 依赖模型提交行为，用户确认采用，未提交不能强制成功 |
| 无进展提醒和停止 | 限制成本，交替读取也能识别 | 提醒不保证模型服从，停止不等于交付成功，用户确认采用 |

## 解决过程

新增工具仅单元开发可用，交付文件由程序根据计划固定，模型不能自行缩减；必须为该工具批次最后动作。缺文件拒绝，齐备后返回待测状态和所有交付文件 SHA-256；普通完成文本最多两次纠正后停止，BLOCKED 保留设计澄清。

提交及恢复都核对实际版本。持久化提交状态后程序执行 Node，失败继续修复、重新提交；已提交版本与测试前文件不一致则拒绝测试该未提交版本。旧 developing 检查点即使文件齐备也必须提交，不能借存在检查绕过。旧任务无开发计划的入口不强制新协议。

无进展按模型批次、当前单元全部交付文件版本统计。同一批多个工具只算一次，交替读、换 description、写入同字节都不产生文件进展；版本变化重置。4 次提醒，8 次停止。该数值是本轮初始有界策略，不是经过统计优化的阈值；纯分析也可能不改变文件，当前不保证识别所有有意义的分析进展。计数证据随检查点保存，提醒在结构化上下文和系统指令出现，不增加原预算或自动调用提交。

## 方案测试与成本

本轮完整 164 项回归，新增 22 项覆盖本问题及 003。Fake 模型与真实文件／Node 检查缺文件提交、错误动作顺序、普通文本不能交接、版本变化失效、提交恢复不重复调用、外部改写、旧检查点和无进展预算。

真实从空产品开始：同一预置三单元设计新增 16 次／73,746 Token，加法提交并测试通过；平方第一次提交后测试失败，修改测试文件后反复读取，未再次提交，8 次无进展触发停止，尚未进入 UI。此前将停止单元记为 UI 有误，本轮对照实际请求与响应纠正。没有因文件齐备强制推进，不能视为完整开发成功。此探针不包含自主架构或设计。

真实返修夹具第一次 16 次／183,824 Token，UI 已修脚本仍没有提交，停止；另一个夹具 7 次／78,234 Token，真实提交后程序测试和浏览器通过。后一个样本未触发 4 次提醒，不证明把提示放进系统指令是成功原因。不同结束状态不可当作稳定节省比例。

## 最终结果与局限

显式交接、版本绑定和成本停止机制工作，且不以文件存在冒充成功；模型仍可能忽略提交，当前设计只保证有界失败，不能保证完成。需继续研究模型行为及成功率，但不在本次偷偷新增强制提交、自动完成或放宽预算。

累计测试 277／300 次含此前所有样本；本轮 39 次／335,804 Token，不仅计成功的 7 次。用户本人验收未执行，真实跨单元故障修复待测。

## 2026-09-18：未提交循环的定位

用户授权定位，未修改运行逻辑，未新增真实模型调用。核对两次失败的实际 sent 请求、不可变模型响应、工具摘要投影和交接状态生成代码。

从零开发的平方单元：第 244 次请求收到第一次测试失败，测试试图改写只读 ESM 模块命名空间。第 246 次调用改写测试文件，文件哈希从 f78e24f4… 变为 adf77241…。第 247 至 254 次请求提供的新文件已无非法赋值，旧反馈仍来自第一次测试；development_state 却持续为 failed／repair_current_unit_from_test_feedback。第 248 次响应明确指出当前代码没有报告中的赋值；第 253 次还指出测试名称与旧报告不同，随后继续读。本轮独立运行现存产品的 node --test tests/add.test.mjs tests/square.test.mjs，退出 0、Node 汇总 7 项通过，平方文件内部还报告 7 个断言通过。该检查只用于诊断，没有代模型提交或改变原失败任务。

UI 返修夹具：第 257 次调用已删除注入的顶层 raise，第 258 次请求快照不含故障表达式；global_failure 和 diagnosis 仍持续要求删除原失败版本第 130 行的 raise。第 260 次响应明确说快照完整且哈希匹配，但找不到旧错误；之后又写一次、继续读至停止。该路径 development_state 为 not_run／submit_unit_for_test，因此单纯修正局部测试 next_action 不能解释或解决全部样本。

已核实的机制缺口：局部反馈本来保存 file_hashes_before／after，但 worker.build_tool_context 只依据 feedback.passed 生成失败与修复提示，没有比较反馈版本与当前文件。集成诊断缓存保存版本，但交给开发循环的 global_failure 没有随本轮修改更新证据适用状态。tool_summaries.project 的 latest_write 保留 ID、状态和哈希，未投影账本已有的 description、result_summary、before_hash，模型也没有收到先前响应中的修复意图。所有请求仍有当前文件全文、完整读取证明和 submit_unit_for_test 工具；未发现文件丢失、全文截断或工具未提供。

判断：两个样本均存在旧失败证据与新文件并列、模型反复确认已不存在错误的现象。当前证据支持「缺少明确的证据版本状态与修复动作含义」是优先处理的架构缺口，不足以证明它是唯一原因，也不证明模型在正确输入下必然提交。无进展提醒已在第 4 次出现而未打破失败样本循环；成功样本也在修改后读了三轮，最后自行识别旧诊断对应旧文件并提交。

开发助手建议，待用户确认：保留旧错误作为历史依据，明确提供 tested_versions、matches_current_files 和修改后待复测状态；相关文件或依赖版本变化后，不能继续把旧失败表达为当前版本的失败，交接提示应区分修复中与修复后待提交。latest_write 增加账本已有的简短 description、before_hash／after_hash 和是否真实改变，不恢复全部对话或全文历史。提交仍由模型明确发起，程序不能把版本变化当作修复成功。先做固定故障的机制验证，再在明确预算内进行真实对照；未实施这些建议。

原始证据：从零目录 /private/tmp/unit-handoff-repair-20260918，sent-244、247、248、253、254.json，以及 traces/develop/1/000049、000058、000080-model_response.json；返修目录 /private/tmp/unit-repair-fixture-corrected-20260918，sent-257、258、260、270.json，以及 000038、000053、000061-model_response.json。HTTP 编号是隔离测试累计实际请求序号，不等同 UUID 模型调用 ID。

## 2026-09-18：开发先自测，再向后续阶段交接

用户确认「开发要先完成自测，自己测试没问题才能交给别人」，并授权调整。原交接要求模型先提交，才能看到新测试结果，修复到提交的推进过度依赖模型判断；仅优化旧证据表达没有给开发阶段直接获得新验证结果的能力。

方案改为开发／修改 → run_unit_tests → 根据真实失败修复并重测 → 当前版本通过 → submit_unit_for_test → 后续独立测试与集成／浏览器验证。相比开放任意 exec，受控自测只执行程序根据开发计划固定的当前及已完成单元 Node 测试，模型不能传命令、范围或跳过要求，维持原文件所有权。

自测返回真实退出码、输出、前后文件哈希和 passed。提交校验交付完整、自测通过、全部测试范围及依赖版本未变；失败自测不授权提交，测试后改代码／测试／依赖均使通过结果过期。检查点恢复真实自测证据，仍需明确提交；旧无自测证明的提交不能恢复。后续程序独立测试继续保留，不将开发自测当成最终验收。旧失败附版本匹配状态，交接提示区分未测、过期、当前失败、当前通过，不把变化当成功。run_unit_tests 输出纳入当前请求工具数据，自测动作及原始结果由现有 Trace／检查点留存。

先更新 Dev Design 的当前有效约定，再实现并验证。完整回归 171 项通过，本轮新增 7 项覆盖实现／测试／依赖变化过期、命令覆盖拒绝与真实失败门禁、真实模型循环的失败→修复→重测→提交（Fake 模型、真实 Node）、旧提交拒绝及自测后中断恢复；原提交与流程测试同步适配。初轮回归发现旧无计划提示兼容与测试模拟中断的异常包装预期问题，修正后完整通过，没有放宽提交门禁。语法和差异检查通过。未新增付费调用，累计仍 277／300 次。

取舍：开发增加主动自测能力，后续独立验证会重复执行部分 Node 测试，先保留该成本以维持验证边界。新机制阻止未经自测的交接，但仍依赖模型主动测试和提交，不能从 Fake 回归推断真实循环已经消失。修改后的真实 DeepSeek 成功率、成本和大任务交付待验证；不把此前先提交后测试的成功夹具作为新协议成功证据。

## 2026-09-18：真实自测故障闭环验证

用户授权在原累计 300 次上限内验证。隔离副本复用此前合成产品与固定设计，首次 add 自测前由测试夹具注入 a-b，真实 Node 10 项中 8 项失败。DeepSeek 根据输出修复实现，之后又读／查询文件，再主动重测，10 项通过后提交；平方自测 20 项、UI 自测 43 项通过后分别提交。程序独立复验、全量 Node 43 项及系统浏览器验证通过，独立 Chromium 18 组通过、页面异常 0，最终等待用户验收。只有 add 实现文件改变，测试和其他产物字节未改，未降低预期或人工代提交。

新增 10 次／65,591 Token（输入 64,629、输出 962），累计 287／300 次、1,812,883 Token。证据 /private/tmp/unit-self-test-deepseek-20260918；详细输入、调用顺序、注入方法、预算与结果见原验证报告末节。测试 summary 的故障标志混用了自测／集成字段，保留原文件并用 audited-results.json 明确本轮未注入集成故障，已纠正后续脚本记录；不单独架构建档。

结论只限一个固定故障的真实闭环：模型确实能在提交前获得失败、修复、重测并交接。新协议未证明稳定成功率提升，也没有从零自主架构／设计／开发证据；成功样本依然出现额外读取，无严格同故障重复对照，不能归因于某单一提示或计算虚假成本下降。

## 2026-09-18：从零复测的阻塞状态未交回设计

用户明确每轮各有 300 次机会；本次独立轮从初始需求开始，没有使用固定设计或产品夹具。加法自测通过后提交，平方主动自测发现公共入口缺导出，且导出文件归加法、开发无权修改。这一单元职责／装配缺口更新于 001。

模型随后无工具返回解释段落加 BLOCKED 问题，已经描述所需设计决定，但 Worker 按 response.text.startswith('BLOCKED:') 判断，未识别夹带前言的阻塞。程序继续要求提交，模型重新读取，最终触发 unit_development_no_progress。原协议要求只输出 BLOCKED，模型未服从；当前状态传递对格式偏差脆弱，不能把没有新写入的全部样本解释为自测意愿不足。

本轮 50／300 次、598,317 Token，预算未耗尽。真实闭环的上一成功样本仍有效，但本轮证明增加自测并不保证自主设计后的全流程完成。建议评审跨单元装配／所有权一致性与阻塞状态的可靠传递，尚未实施。详细阶段、实际输入与控制介入见 [从零复测报告](../evidence/self-test-full-flow-deepseek-validation.md) 。

## 2026-09-27：精确替换与返修无进展控制

内容工作台验收返修中，提示词要求大文件使用 `replace` 修改，模型也成功替换了 `verify_product.py`，但无进展计数只把成功 `write` 当作写入，误将后续读取和测试挡为 `repair_tool_loop_no_write`。现将成功的 `replace` 同样视为进展；回归测试覆盖成功替换重置计数、失败替换不重置，后端全套 221 项通过。这只修复机制误判，不会自动提交或放宽调用上限。

续跑中模型仍在验证脚本上持续读取、替换和自测，最终 `unit_development_no_progress`；独立浏览器的素材编辑入口仍缺失。无进展保护按设计有界停止，但无法保证模型优先处理原始验收缺陷。累计 128 HTTP／12,026,798 已报告 Token 含从零生成及多段诊断续跑，不能视为单次无人干预成功。完整调用和干预边界见 [编辑验收续测](../evidence/content-workbench-edit-acceptance-continuation-20260927.md) 。
