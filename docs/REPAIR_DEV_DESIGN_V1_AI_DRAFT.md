## 1．入口与旧任务兼容

建议在已有 Event API 增加 `repair_request`，不新增数据库表。用户输入问题和选择采用新返修方式；客户端补充 expected_task_version、执行方式及被选中的产品版本，内部字段由程序核对，不要求用户编写执行卡。

| 字段 | 语义 |
|---|---|
| feedback | 非空原始问题，保留原文 |
| expected_task_version | 乐观版本校验，冲突返回明确原因 |
| workflow | 新尝试明确指定 `repair-v1`，缺省沿旧入口 |
| budget_authorization_ref | 已确认的本轮范围、Provider、外发数据和新增请求上限依据 |

可接收来源：同任务 waiting_acceptance、succeeded 或 failed，且完整工作区／有效需求／原累计计数可核对。running／pending、正在等待其他产品决定或产物缺失时拒绝并说明原因。服务器核对当前产物而不采信客户端哈希，其他目录路径不成为导入入口。

旧 acceptance_result、change_request 和 user_message 语义保持。repair_request 显式授权恢复失败任务，创建新尝试，保留旧失败 Run；同 Event 只初始化一次。未选择新执行方式不创建新状态记录。采用旧任务的新方式不等于批准重置预算。

## 2．存储、所有权及版本

每个返修尝试使用现有 Task 工作区；新增以下程序专有文件，实施前登记目录约定，原记录不覆盖：

- `evidence/repair-runtime-v1.json`：执行方式、授权引用、当前尝试、会话、阶段状态、预算和提交引用。
- `evidence/repair-attempt-<event_id>-submission.json`：不可覆盖的提交及版本依据。
- `evidence/repair-attempt-<event_id>-validation.json`：阶段结果、版本、目标与完整证据引用。
- `evidence/repair-session-<session_id>-checkpoint.json`：连续模型工具协议与恢复信息。

沿用原 repair-objectives.json、Message、Trace、工具摘要和正式需求文档。不同记录的权威范围明确：Task 管理对外状态和任务身份；runtime 管理本执行方式的内部阶段／预算；原目标账本管理反馈与核销；Trace 管理原始证据。版本包含文件清单及内容哈希，新增、修改、删除文件都改变版本。

模型可以只读所需证据，不能经文件工具写 runtime、账本、检查点、正式需求或验收标准。服务 PID／URL 属程序事实，不能由模型直接更新。

runtime 是可更新的当前状态视图，原子落盘并带递增 revision；各次授权和提交以及旧尝试的不可变证据保留，Trace 追加不变记录。数据库投影随后提交。恢复时通过 last_event_id、阶段结果和 revision 幂等修复投影，缺失或冲突时阻塞，不能从数据库当前状态猜造已完成阶段。单 Worker 前提下不引入分布式锁，文件与数据库不宣称整体原子事务。

## 3．内部状态与外部投影

| 内部状态 | Task 投影 | 含义 |
|---|---|---|
| executing | running／develop | 同会话调查、计划、修改和自测 |
| waiting_decision | waiting_user | 存在未确认关键决定，持久保存具体问题与提议 |
| submitted | running／test | 提交已持久化，版本冻结 |
| testing | running／test | 当前提交全量测试 |
| starting | running／start_product | 托管服务与 HTTP 健康检查 |
| verifying | running／verify_product | 当前提交真实浏览器检查 |
| reviewing | running／verify_product | 独立只读目标审查 |
| awaiting_acceptance | waiting_acceptance | 当前版本全部门禁通过 |
| accepted | succeeded | 用户明确验收该提交 |
| stopped | failed | 原因独立记录，禁止自动恢复 |

对外复用现有枚举，不把阶段标签解释为更换模型。TaskResponse 建议增补可选字段 `execution_mode`、`repair_state`、`stop_reason`、`budget`、`submission_id`；旧任务这些字段为 null，前端继续兼容。

## 4．执行会话契约

一个返修尝试拥有一个主要逻辑 session，固定 Provider 和提示词版本，默认 DeepSeek thinking。session_id 不依赖 StepRun；跨阶段修复时恢复原目标、当前计划、有效文件证据和未完成目标。阶段 Run 负责审计，但不另起 Planner 决定固定动作。

执行 Agent 可使用受控 search／read／write／replace、run_unit_tests、submit_for_verification、request_decision。业务文件修改权限在第 6 节定义。它不能直接推进 Task、核销目标、批准自己提出的产品改变、启动产品服务或调用任意 shell。

局部计划写入受控工作状态并记录修订原因；计划用于目标与进度，不产生永久文件所有权。调整实现顺序无需用户再次批准；改变业务、重要接口语义、数据规则或授权范围先 request_decision。

独立目标审查为单独只读上下文，不能改代码或执行控制。技术 Provider 降级不直接迁移专有思考历史；首版建议主会话 Provider 固定，技术失败停止并等待明确恢复，不新增自动切模型策略。

## 5．当前任务视图与读取

每轮最少提供原目标引用、有效需求版本、授权、当前计划、当前代码版本、最新适用失败、自测／提交状态和剩余请求额度。详细旧报告与旧卡保持可查询，不每轮重发正文。

search 在已授权读取清单内按文本定位，返回路径、行号、命中片段、当前哈希及截断／续查信息；不向模型暴露宿主路径、shell 或越界 glob。建议首版限制单次最多 50 条命中，read 默认 200 行，结果受现有字节上限约束，参数和输出均明确范围。

按文件版本和实际返回范围登记已知内容，不把截断或局部读取当全文。相同版本、同范围内容仍在请求中时不重复发送；已省略、失效或变更的内容允许按权限重新获取。完整审计不删。DeepSeek 当前工具轮次的必需 reasoning_content 和 call_id／tool 结果配对保持；不能把删除历史思考当压缩策略。

合法完整批次边界可沿用现有上下文接力思路；有效正文、任务事实与引用必须可恢复。纯读取不算提交，少 Token 的请求不构成完成证据。

## 6．权限及命令运行

程序根据已批准任务建立读取／写入清单，包含该任务 product 下实现和测试；不从旧责任卡推断。新增相关文件需受清单规则及路径校验约束。正式需求、保护文件、凭据、审计和其他任务不可写。删除文件、安装依赖等高风险动作仍需单独授权，首版不新增模型删除或安装工具。

修改已有测试必须保留原始目标和回归依据；提交记录测试 Diff，独立审查依据原需求及固定回归判断，不以模型声称「测试错了」授权弱化业务条件。

run_unit_tests 的命令及范围由程序固定，范围包含当前产品测试和已确认回归，不让模型选一个绿灯子集作为完整提交依据。自测结果记录执行命令、退出码、stdout／stderr、前后版本、时间与结果；运行期间代码变化则证据失效。

生成代码目前在宿主子进程运行，文件工具保护不能控制其副作用。最小凭据传递、文件写入范围、子进程与网络规则必须通过确认的运行隔离实现；具体技术待决定，不能用工作目录或命令白名单宣称沙箱。权限扩大和真实新模式执行前必须验证该条件。

## 7．显式提交

submit_for_verification 请求包含目标完成说明、已知限制、实际修改文件及自测证据引用。程序核对：有实际有效自测、当前版本与自测一致、需求及授权版本未变、固定入口存在、修改未越权。失败返回具体字段／版本原因，继续原会话。

成功后程序持久化提交 ID、全量版本清单与证据，锁定本任务写入，停止该执行循环并开始验证。不因单次自测成功、文本结束或读取停滞自动提交。遗漏目标可以在独立核验时检出，不通过修改提交说明自行核销。

如果自测通过后模型继续读取必要信息，仍可读取；进一步修改会使自测失效，须重新自测再提交。预算耗尽则 stopped，不能以程序替代模型的完成判断。

## 8．固定验证流水线

1. 核对冻结版本、需求和授权；每个阶段前后均核对版本，发现外部编辑立即使该阶段证据失效。已完成且同版本的阶段结果可恢复复用。
2. 执行固定全量 Node 测试，检查失败、skip／todo 和已确认要求。
3. 程序核对并托管服务，保证 URL／PID 对应本任务；已有同目录、同入口服务可复用，但要验证实际托管版本与 HTTP。需要重启时遵循运行任务和授权边界。
4. 对冻结版本执行真实 Playwright 脚本预检和操作验证，不允许 skip 冒充执行。验证包括页面异常与控制台错误，以及原始业务要求和错误后恢复。
5. 独立只读审查原始目标、实际执行脚本和运行结果；仍沿用目标 ID、逐字操作／断言引用、完整结果及版本核对。独立审查可能误判，不能声称形式化证明全部业务覆盖。
6. 所有必需目标核销、证据版本有效且 URL 可访问时，程序确定性进入 waiting_acceptance；不再调用 Planner 选择 test、start_product、verify_product 或 finish。

实现／测试／覆盖缺口：保存新失败但不覆盖原目标，解除冻结回 executing，沿同 session 修复。服务环境错误、程序验证器错误或不确定副作用：stopped，明确分类，不能默认引导模型修改产品。浏览器操作超时先保留实际证据，不无证据归因为实现问题。

目标关闭记录绑定本次代码、脚本、需求和运行证据。新版本修改后旧关闭结果失效。用户通过验收也必须对应当前 submission；陈旧事件拒绝，不能验收另一个版本。

## 9．实际请求预算

建议在 Provider 的实际 HTTP 发送入口维护任务级持久账本，旧 StepRun.model_call_count 继续表示逻辑请求，两者不混用。重试、审查及任何受控降级均受总上限约束。

| 字段 | 含义 |
|---|---|
| historical_attempts | 启用时核对的原已用次数；缺失不得猜作零 |
| total_limit | 原计数加本次批准额度，只有明确新授权才能增加 |
| attempts_used | 请求前原子登记的保守已用次数，发送不确定也不回减 |
| review_reserve | 本轮授权确认的审查预留，执行阶段不能占用 |
| authorization_ref | 本轮目的地、数据范围与预算授权 |
| response_usage | 实际已知输入／输出／总量与未知响应，引用原 Trace |

执行请求超过 total_limit 减 review_reserve 时停止执行并保留当前成果；审查可使用余下额度，但不能超 total_limit。预留比例不固定为通用默认，本轮真实调用前确定。请求前登记后、HTTP 尚未发送就中断的预约保守保留，另标发送状态未知，不谎报确定发生的 HTTP。

使用独立 `BudgetExceeded` 边界错误；它不进入网络重试、降级或通用 RuntimeError 包装。Token 实际统计可能缺失，不承诺以输入估算严格控制总 Token；首版硬上限为请求尝试数及程序时间限制。重启和新 Run 不增加额度。

stopped／budget_exhausted 恢复必须有新的具体授权，通过受控事件追加额度，沿原累计次数继续。未经授权不自动核销目标、降低验证或续跑旧 Task 1。

## 10．等待决定与用户回答

request_decision 持久化问题 ID、问题原文、影响、提议和相关产物版本，Task waiting_user，不从标点推测等待事项。user_message 或确认事件绑定当前问题，由程序记成成对问答。

只有明确确认的决定更新有效授权／设计版本；批准后新上下文接收决定和影响，旧需求证据失效并按范围重验。拒绝保留原方案及理由，执行 Agent 修改方案；不把模糊回答自动视作设计变更批准。首版不自动实施产品大改动或数据迁移。

## 11．恢复与幂等

| 中断位置 | 恢复规则 |
|---|---|
| 事件初始化 | 同 Event／revision 复用原尝试与预算，补投影，不另建空尝试 |
| 请求中途 | 保留计数和部分响应，无完整结果不执行工具；供应商响应重试另计请求 |
| 文件修改与检查点之间 | 依据不可变工具参数、写前／后哈希和已存结果核对；可确认完成不重做，冲突停止 |
| 命令启动后 | 核对原 PID、命令、工作区和证据；无法确认结果则 unknown_side_effect，不自动再次执行 |
| 自测后 | 恢复同版本自测；文件变化则失效，不授权提交 |
| 提交后 | 从持久提交和当前版本恢复尚未完成验证；版本冲突明确停止 |
| 目标关闭后 | 核对代码／需求／浏览器版本，修复待验收投影；无依据不重建成功结果 |

程序自测和浏览器可能产生副作用，不能笼统称为可安全重放。浏览器使用隔离测试数据与受控上下文；无法证明确切结果时停止，由运行控制决定后续，不宣称所有操作 exactly-once。

## 12．测试、真实验证及实施划分

### 第一批：固定验证收尾

复用现有自测／提交和测试／启动／浏览器实现，增加新执行方式明确入口及持久验证状态、版本检查、预算错误分类与最小 Provider 请求守卫。现有写权限及执行会话先保持，取消固定步骤间 Planner；旧任务兼容。验收是提交后完整流水线不需要模型决定确定动作，失败／陈旧证据不能推进。

### 第二批：连续会话与范围

新增逻辑 session、受控提问和计划状态，返修调查与执行合并，验证失败回原 session，权限按任务范围。前提是执行隔离技术确认及验证；此前不能宣称跨文件新模式可安全启用。

### 第三批：读取与成本

接入受控搜索、统一有效文件范围、上下文接力和实际用量展示。不额外调用摘要模型，Provider 协议历史保留。以真实到完整交付的成本评价，不只比较请求字符数。

必要机制回归覆盖：有自测无提交、有提交但新修改、旧验收事件、新增文件导致旧哈希失效、预算耗尽不重试、重启次数保持、跨阶段会话保持、原目标不覆盖、保护文件拒写、未知命令不重放及同 Event 去重。正常成功和失败路径都要验证。

真实实验从完整持久副本、明确需求和授权开始，分别验证局部缺陷、跨模块及恢复，并加入未针对调试的新缺陷。同起点／目标／上限对照，独立 UI 验证，记录所有失败和人工控制介入。当前已修 favicon 不能冒充新的未知任务。请求范围及额度另行确认。

## 13．确认决定及实施前置条件

1. 产品首版限于本项目已有原生网站任务，采用显式新返修尝试，旧生成流程兼容。
2. 一个主要 DeepSeek 会话，独立只读目标审查；显式自测和提交保留，固定推进取消 Planner。
3. 产品目录任务范围写权限与保护记录边界；扩大前选择并验证命令运行隔离技术。
4. 单 Worker、现有数据库表与版本化工作区状态，阶段状态为对外投影；不同存储不宣称整体事务。
5. 任务级实际请求尝试上限与审查预留，耗尽明确停止；真实实验额度单独批准。

用户于 2026-10-05 明确「确认」本组方案，随后要求先推送现有代码。先保存当前实现与确认记录，下一步按第一批更新有效规范并实现固定验证收尾。命令执行隔离选型仍是第三项权限扩大的前置决定，真实实验额度单独批准；本次确认不自动选择隔离技术、迁移旧任务或新增付费调用。
