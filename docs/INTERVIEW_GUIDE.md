## １．项目定位

一句话：**面向已有网站返修的 AI 执行系统，围绕目标、版本、预算、隔离和验收建立可追溯闭环。**

已有生成流程是实验来源，目前架构升级重点是开发失败后的调查、修改、自测和交付。产品决策及最终验收由用户负责，模型在授权范围内执行，程序管理可确定的动作与安全边界。

一分钟讲法：

> 我做的是已有网站的AI返修系统：模型负责调查和修改，程序在模型明确提交后冻结版本，执行全量测试、实际浏览器操作，最终由用户验收。执行用Docker隔离，预算按实际HTTP尝试累计，失败和重试也计数。优化中遇到一次反例：同一两文件故障，离线正文缩减57.2％，真实Token却从39.66万涨到71.99万。我核对实际请求，发现省略已读依赖引发补读，同时模型定位后仍持续调查。随后恢复必要上下文、澄清修改记录，并让新会话围绕具体未决问题推进、合批修改。最新一次11次调用、24.96万Token，原150项Node和60条浏览器验证通过，无人工改码。这是联合改动后的单例改善，耗时反而变长，不能宣称稳定降幅；目前保留该版本，成本仍需优化。

## ２．最值得讲的三个工程问题

### 问题一：为何自测通过仍不能自动交付

真实现象包括：模型重复读文件不提交，以及程序诊断通过后模型继续补业务断言。单纯「测试绿就结束」可能截断尚未完成的修改；完全依赖模型自行收尾又可能不收敛。

当前取舍：保留主动自测和显式提交；修改使自测失效。明确提交后冻结全产品版本，程序确定性完成后续验证，新尝试取消独立模型目标审查，人工验收保留；旧尝试保留原契约。验证失败回原主会话，不重新由 Planner 选择确定动作。依据：[004 交接问题](architecture-issues/004-unit-handoff-and-progress-control.md) 、[第二批验证](evidence/repair-session-validation-20261009.md) 。

可追问：新增文件会不会漏算？旧验收事件能否接受新代码？未知工具副作用怎么恢复？回答都应落到文件集合／内容哈希、提交 ID／任务版本、持久意图／结果及禁止自动重放。

### 问题二：上下文变短，为什么仍会失败

真实失败既有大量重复正文，也有省略正文后系统仍禁止再次读取的情况。文件哈希和摘要不是代码正文，历史读过不等于模型当前看得到。

当前取舍：原始 Trace 和协议证据保留，模型请求按有效版本与实际可见范围构建；思考模式保留必需 reasoning_content 和调用配对。旧报告提供可恢复引用，不能以「省 Token」删除关键业务事实。受控搜索、分页版本校验、实际可见范围去重及完整批次独立上下文接力已实现，并完成素材检索故障的真实模型对照；跨任务稳定效果仍未验证。依据：[002 上下文问题](architecture-issues/002-tool-context-and-execution-memory.md) 。

#### 可直接讲述的案例：测试绿了，模型为何还在调查

**问题与证据。** 同一素材笔记检索故障的第三轮真实返修，自测通过后仍花5轮才提交。核对实际请求发现：当前通过状态、过期读取摘要、最后一批修改及待审查的原目标并列。接力只列最近修改，模型需要重新拼出累计进度。模型确实继续查询历史和验证脚本，但不能据此断言单一原因。

**方案与取舍。** 程序从原runtime和检查点提供一份当前事实：累计成功写入、最新版本适用性、自测、最新独立失败和审批状态。模型用原update_plan可选保存findings、open_questions和next_action，明确标为判断，版本变化后需复核。没有增加总结模型或第二套进度存储；历史仍可查询，必要正文可补读，测试通过仍须模型显式提交。旧会话不迁移。

**如何验证。** 先离线投影三轮保存的41份实际请求，再做失效、独立失败、未知动作、决定恢复和旧契约回归。随后用相同完整平台、批准文档和注入缺陷做一次有界真实DeepSeek对照，最多20次HTTP。模型修复后，以保存的原断言独立Docker复测，避免拿被模型修改的测试自证正确。

| 指标 | 上一轮 | 当前事实＋模型进度 |
| --- | --- | --- |
| 实际HTTP | 13 | 8 |
| 总Token | 292,780 | 155,482，减少46.89％ |
| 耗时 | 72.7秒 | 56.5秒 |
| 最后自测通过到提交 | 5轮 | 3轮 |
| 原断言独立验证 | Node149项／Chromium55条通过 | Node149项／Chromium55条通过 |

**局限。** 两轮均无人改码或纠错，但上一轮新增一项回归，本轮没有新增测试，随机轨迹和工作量差异影响成本。新视图与模型工作判断实际生效，历史确认及单独计划调用仍存在。可以说单例部分改善，不能说稳定降低46.89％、成功率提高，或只靠上下文结构就解决了所有问题。

**追问准备。** 为什么不测试通过就自动结束？因为测试不能覆盖全部业务，模型可能仍需修改。为什么模型判断不能当事实？因为它可能过期或错误，不能清除真实失败、批准设计或关闭验收目标。为什么保留历史查询？因为当前视图不能预先包含所有调查所需信息。为什么不马上再测十次？当前证据只支持单例结论；下一次实验应针对明确剩余风险，并另行限定范围与预算。

依据：[完整真实对照](evidence/material-search-current-facts-deepseek-real-20261009.md) 、[机制与离线验证](evidence/repair-current-facts-validation-20261009.md) 。

历史单样本同断点到交接：11 次 HTTP／474,035 Token，相比旧同范围 678,715 Token 少 30.16％，但调用与读取增加；后续交付门禁失败，不能说整软件成本下降或成功率提高。依据：[真实比较](evidence/context-slimming-deepseek-real-20261003.md) 。

### 问题三：文件权限为何不能代替执行隔离

限制文件工具写路径，不能阻止生成测试脚本读取 Worker 环境或访问其他目录。模型生成的 Python／Node 运行能力需要独立控制。

当前取舍：宿主管认证、预算和任务状态，SandboxRuntime 管任务／版本／动作／证据，Docker 承载固定 Node／HTTP／Chromium；只读冻结产品、断网、非 root、资源限制，宿主可信静态服务预览同版本。没有新增多后端框架或数据库表。

真实探针检出 Chromium chroot 兼容、未知动作停止判定及预览 TIME_WAIT 问题，修复后实际资源耗尽、超时整容器停止及同地址重启持久化通过。它证明本机支持范围内的边界，不证明任意恶意代码或多租户生产安全。依据：[Sandbox 证据](evidence/sandbox-isolation-real-20261009.md) 。

### 负优化是怎么发生、怎样定位的

**最初假设。** 返修接力未识别当前自测，回退到携带此前全部已知范围；v2嵌套自测又与工具消息及失败摘要重复。于是接通证据入口、精确去重，并只携带修改文件，其余留引用、允许补读。

**离线结果看起来很好。** C1十二轮user正文从484,628降到207,220UTF-8字节，少57.2％；接力正文60,837→13,482字节，原assistant／tool协议保持。这个结果只证明序列化体积变化，不是供应商Token或模型行为证据。

**真实测试否定了成本假设。** C2实际聚焦正文13,600字节，精确去重也生效，但总Token增到719,905。自测通过后9次read中6次重取被省略的同字节范围，包含tasks、跨模块测试、dashboard、浏览器脚本。模型思考明确提到已读tasks没有携带，需重新检查。未修改文件仍可能是修复判断所依赖的业务链证据。

**没有把全部增长甩给一个原因。** 两轮首个请求除调用ID外相同，首次响应的读取批次已不同。净增量323,297Token中，首次通过前多260,045、通过后多68,918、审查少5,666；约80.4％净增量发生在通过后聚焦启用之前。模型两轮第3轮都定位两个故障，但C1第6轮同批修改，C2第13／14轮分别修改。实测倒退明确，全部因果仍不能由单样本确定。

**撤回依据。** 撤回仅按修改文件筛选，保留原实际已读范围、准确去重和必要补读；修改记录直接标明write／replace，避免query_tool引用被误读为修改工具。两轮14份原接力请求离线核对，原思考、协议及原实验字节不变，恢复正文覆盖6处旧范围，现有重复保护实际拒绝这6处。C2轨迹恢复正文会到95,981字节，这是为连续性接受的单轮成本，不承诺真实调用立刻少6次。

依据：[正文成本修正](evidence/repair-context-cost-validation-20261009.md) 、[连续性恢复](evidence/repair-context-continuity-validation-20261009.md) 。

### 定位后调查太久，为什么没有再加硬限制

逐项核对C2发现，视图、计数、批准接口核查有价值；来源选题缺失占位是另一个场景，被扩成本次修改前置，额外UI／浏览器脚本调查也推迟了修改。原因不是程序强迫它读；模型思考说要自测，实际还在搜索。

用户确认后仅对新会话增加软性规则：围绕影响本次修复的具体未决问题调查；依据充分时优先改测；独立无关疑点先记录；独立动作尽量合批。缺证据／设计冲突仍可调查或request_decision。没有按读取次数强制结束，没有绿灯自动提交，也没有强制每轮调用update_plan。原v2与legacy按原提示词哈希恢复，83项机制回归与两份真实旧绑定核查通过。

C3实际第7轮同批修改，第8轮通过，第10轮计划与提交合批。但update_plan的steps误发字符串而非数组，被正常拒绝；计划不是前置，同批显式提交合法，独立验证通过。可选工作进度并未保存，不能讲它帮助本轮收尾。

依据：[逐项评审](evidence/repair-investigation-progress-review-20261009.md) 、[实施与旧绑定验证](evidence/repair-investigation-progress-validation-20261009.md) 。

### 面试追问与当前真实评价

- **上下文越短越好吗？** 不一定。总代价取决于每轮输入、调用次数、补读和审查。只优化正文体积可能丢失判断依赖，让模型重新调查。
- **C3是提示词优化成功吗？** 只能说联合修正后的这次交付与成本改善；恢复依赖、明确操作和新提示词共同变化，且C3只有修改后一次主动自测，C1／C2均先失败再通过，不能归因提示词独立效果或外推稳定性。
- **为什么保留负优化？** 它直接检验了错误假设，并给出撤回方案的依据。39.66→71.99→24.96万这条轨迹比只展示65.33％降幅更真实。
- **目前有什么没做好？** 两个明确缺陷仍用约25万Token，独立审查53,111Token占21.3％；调查仍到第7轮才修改，计划参数错误，耗时增至165.9秒。成本尚不合格，成功率和稳定收益未证明。
- **现在的决定是什么？** 用户确认保留现版本；不继续压缩上下文、不自动付费重跑。随后用户确认取消新尝试的独立模型审查，机制验证通过；真实成本收益仍待验证，不自动付费重跑。

七次新返修实验合计101HTTP／2,875,044Token，旧素材平台220另算；累计数字代表学习与验证成本，不是一个任务成本。每轮持久证据可复核，但本地留存不是异地备份。当前结论是有限任务真实交付成立、单例成本改善，最终用户验收与更广范围能力仍分开。
